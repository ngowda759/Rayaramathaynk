# Aaradhane scheduled writer — Supabase cutover plan (PR-D4)

Status: **PARTIALLY IMPLEMENTED.** The writer, the Firestore-write retirement and the
guard/test work described below are implemented in code on this branch. Production
migration status stays **HOLD**: no schema change has been applied, the workflow
still does not write, and no data has been moved.

## 0. Owner decision and what "done" means

The owner's decision is that **Firestore must receive no writes from the Aaradhane
system. Supabase is the target and the sole database for all Aaradhane data.**

That decision is stronger than "disable the workflow". Disabling the scheduled job
alone leaves every other write path intact — the module the job called, the
standalone generator, the seeders, and the second Firestore writer to the same
collection. The requirement is therefore that the *application code* moves, not just
the schedule:

- the Firestore Admin SDK persistence is **replaced** by a Supabase/PostgreSQL
  implementation built on the existing Supabase clients;
- the **writer** is replaced, not wrapped;
- every consumer of the generated events — the live cron and the admin readers — is
  accounted for.

What this branch delivers toward that:

| Requirement | State |
|---|---|
| Supabase writer replacing the Firestore Admin SDK writer | Implemented (`lib/aaradhane/supabase-writer.ts`) |
| Firestore write paths removed from the execution path | Implemented (4 modules + 4 scripts deleted; workflow credential step and write step removed) |
| `environment: production` on the database-writing job | Implemented (see §3.6 and the caveat in §6) |
| Destination guard before the first connection | Implemented (reuses `guard-approved-project.mjs`) |

## 1. Why this is a separate, destructive-adjacent problem

`.github/workflows/aaradhane.yml` writes to the Firestore **`events`** collection on a
schedule, and it does so **by default**:

- `workflow_dispatch` declares `dry_run` with `default: false` (lines 15–19).
- On a `schedule` run `inputs.dry_run` is **empty**, so the live step's guard
  `if: inputs.dry_run != 'true' && steps.check_panchanga.outputs.exists == 'true'`
  (line 254) is satisfied and the step at line 269 runs
  `scripts/generate-aaradhane.ts --year $TARGET_YEAR` **without `--dry-run`**.
- `--firestore` in `scripts/generate-aaradhane.ts` only selects the **read** source
  (Firestore `guruParampara` vs the local file). It does not gate the write. The write
  happens on any run that omits `--dry-run` (`scripts/generate-aaradhane.ts:230-235`).

So the workflow is a **scheduled database writer with no destination guard**, and
`events` cannot be cut over by migrating rows alone: the workflow must be retired or
re-pointed. This is why the cutover is its own change and not part of PR-A2.

**The write is armed right now, and the cron gate is not protection.** The live step is
gated on the panchanga step's output, evaluated before any generation runs
(`aaradhane.yml:254`): `if: inputs.dry_run != 'true' && steps.check_panchanga.outputs.exists == 'true'`.
`check_panchanga` (`:75`) sets `exists=true` only when
`data/panchanga/<TARGET_YEAR>/` already exists in the checkout, and the cron targets
`CURRENT_YEAR + 1`. As of 2026-10-22 the target is **2027** and
`data/panchanga/2027/` exists (365 files), so `exists=true` **today** — any
`workflow_dispatch` without `dry_run=true` reaches the live write step immediately.
The one tick the gate protects is the next cron fire (2027-01-01, target 2028, no
panchanga directory), and that protection disappears the moment 2028 panchanga is
committed. The guard must therefore land **before the next dispatch and before the next
panchanga commit** — there is no grace period. Readiness review §5.

### 2.1 Correction to the existing backlog

`docs/FIRESTORE_SUPABASE_MIGRATION_BACKLOG.md` §1.1 states the writer uses
"deterministic IDs `generated-<year>-<slug>`" and that "all writes are idempotent by
ID for a given year", and §4 repeats the same key form. **The code does not do this** —
creates use a random auto-ID and updates rely on a heuristic match. The
`generated-<year>-<slug>` form is a *proposal*, not current behaviour. §1.1 has been
corrected in this change; §4 is retained as the proposal it is.

## 3. Design

### 3.1 Deterministic IDs

Write `firestore_id = \`${guru.id}-${year}\`` — the existing `eventKey`
(`generator.ts:211`) **as-is**. This is already the shipped convention:
`data/exports/supabase-events-2027.json` contains `madhvacharya-2027`,
`raghavendra-poorva-2027`, `raghavendra-madhya-2027`, `raghavendra-uttara-2027`.

Two corrections to the earlier draft of this plan, both from the readiness review
(`docs/AARADHANE_CUTOVER_READINESS_REVIEW.md` §2):

- **No `generated-` prefix.** The prefix appears nowhere in `scripts/`, `lib/`, `app/`,
  `services/` or `data/`. Adopting it would make the scheduled writer disagree with
  `npm run migrate:events-from-json` (`scripts/migrate-events-to-supabase-from-json.ts`),
  duplicating every row under two `firestore_id` values.
- **No phase suffix.** The three Raghavendra phases are already **separate guru records**
  with distinct IDs (`data/aaradhane/gurus.ts:311,327,343` — `raghavendra-poorva`,
  `-madhya`, `-uttara`), so `${guru.id}-${year}` already disambiguates them. A suffix
  would produce `raghavendra-poorva-2027-poorva`. The "two phases collapse onto one row"
  risk below is real only if `guru.id` is omitted from the key.

### 3.2 Idempotent upsert

`upsert(rows, { onConflict: "firestore_id" })`, reusing the repository's established
shape (`scripts/migrate-events-to-supabase-from-json.ts:28-30`,
`lib/supabase/migration-runner.ts:142,150-154`): batch upsert first, then a
**row-by-row retry** if the batch fails, so one bad row does not lose the year.

Two guards the existing precedent does not have and this path needs:

1. **Ownership.** Only rows whose `firestore_id` is `${guru.id}-${year}` for a guru in
   the generator's own list may be written. **The `auto_generated` / `year` columns this
   guard would naturally read do not exist**: the writer emits 19 fields and the
   Supabase `events` table has columns for only 9 of them
   (`20260907112632_create_core_tables.sql:53-70`; `CORE_FIELD_SPECS.events`,
   `lib/supabase/migration-mappers.ts:668-682`). Add `auto_generated` and `year` (and
   see §3.3) in the same migration as the date columns, or enforce the filter in code
   against the generated set. Readiness review §4.
2. **Deletion policy.** A re-run must never delete rows it did not generate. If the
   expected set for a year shrinks, the stale generated rows must be left alone or
   removed by an explicit, separately authorised step — never by an implicit "delete
   rows not in this batch".

### 3.3 IST date handling

Aaradhane dates are **Indian civil dates**. The correct representation is a plain
`date` (`2027-04-16`), not an instant.

The `events` table currently has `start_date timestamptz` / `end_date timestamptz`.
Storing an Indian civil date as `timestamptz` at UTC midnight renders as **05:30 IST**
on the same day, and is wrong for any consumer that formats in a non-IST zone. The
multi-day derivation in `lib/aaradhane/panchanga.ts:168-176` round-trips through
`toISOString()` (UTC) at a fixed offset; it is self-consistent for UTC-midnight values
today, but it is fragile and couples the date to the process time zone.

Recommended destination shape (a **schema change**, therefore a separate reviewed
migration — not part of the writer PR):

- Add `start_on date` / `end_on date` columns for civil dates; write the panchanga
  date string directly. Keep the existing `timestamptz` columns for non-Aaradhane
  events that genuinely carry a time.
- Derive the target year in `Asia/Kolkata`, never from a UTC timestamp.

If the owner prefers to avoid a schema change, the fallback is to store UTC midnight
and have every reader format in `Asia/Kolkata`. This is the weaker option: it hides the
civil date inside an instant and will break for any reader that does not know the
convention. The plan assumes the column addition.

### 3.4 Retries

No generic retry helper exists in the repo (only `scripts/seva/seed-demo-data.ts:1269
retryingRpc`, and the row-by-row fallback above). Reuse the batch-then-row-by-row
pattern rather than inventing a second retry mechanism. Add bounded retry with backoff
for transient network/5xx errors only, and fail the job loudly on a non-empty expected
set that produced zero rows (the backlog's monitoring note, §4).

### 3.5 Explicit dry-run protection

The current default is dangerous: absence of a flag means *write*. Invert it.

- The writer must require an explicit `--apply` (or equivalent) to write. A run with no
  flag computes and reports, and writes nothing.
- `scripts/generate-aaradhane.ts` keeps `--dry-run` for compatibility, but `--dry-run`
  and the new "no flag" path must both be non-writing.
- The workflow's live step must pass the explicit write flag; a `schedule` run must
  **not** reach the writer at all until the cutover is deliberately enabled.

### 3.6 Workflow re-point (the B-1 part)

**Implemented on this branch:**

1. Removed the Firestore write (`updateFirestoreWithAdmin`), the
   `firebase-admin-key.json` materialisation step, and the
   `FIREBASE_SERVICE_ACCOUNT` / `GOOGLE_APPLICATION_CREDENTIALS` wiring. The workflow
   can no longer authenticate to Firestore at all.
2. The former live step is retained under its original condition but always passes
   `--dry-run`; no step in the workflow passes `--apply`. This keeps the job structure
   and its trigger intact while removing the write, so nothing about the schedule
   changes behaviour beyond the write itself.
3. Added the canonical destination guard **before the first connection or write**:
   `scripts/lib/guard-approved-supabase-url.mjs`, the same guard the two Firestore
   migration workflows use. The writer authenticates with
   `NEXT_PUBLIC_SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`, not a project ref, so the
   URL guard is the one that checks the credential actually in use. No new guard was
   written.
4. Added `environment: production` to the job, matching the other write-capable jobs.
   See the caveat in §6 — this is not a working approval gate until the owner
   configures required reviewers.
5. Deleted `scripts/generate-events-firestore.ts` and `scripts/import-events.ts`. The
   former was a **second** Admin-SDK writer to the same `events` collection invoked by
   no workflow, so a workflow census would never have surfaced it; the latter
   `add()`ed every row with no de-duplication.

**Held (not done, deliberately):**

6. The Supabase write is **not** enabled in the workflow. The step that would call the
   writer still does not exist; enabling it is PR-D4b and requires the schema decision
   in §3.2.
7. No `concurrency` group was added. The scheduled path performs no write, so
   interleaving is not currently possible; a `concurrency` group belongs with the step
   that enables the write.
8. The `trigger` on the inventory entry is recorded as `scheduled` because the cron
   remains. The entry asserts the guard and environment binding, not that a write
   occurs.

### 3.7 Inventory / test coverage

**Implemented on this branch:**

- `tests/unit/workflow-writer-inventory.ts` deliberately excluded Firestore-only writers
  (`DB_SIGNALS` is Postgres-specific). Now that the Aaradhane writer targets Supabase it
  **is** a Postgres writer, so `aaradhane-generate` was added to `DB_WRITER_INVENTORY`.
  The completeness test now enumerates **eight** writers, and a fixed count makes a ninth
  a conscious decision rather than a silent widening.
- Two detector gaps were found and closed while adding the entry:
  - The command matcher compared a command's tokens with a single literal space, so
    `--project "tsconfig.scripts.json"` (a quoted argument the shell would strip) did not
    match and the writer would have been invisible. It now matches `\s+` between tokens
    and tolerates a quoted argument.
  - `referencedScripts` only saw literal `scripts/…` paths, so a workflow that ran the
    writer through `npm run generate:aaradhane` — which invokes `npx tsx`, a different
    command string — named no path and would not have been enumerated. It now resolves
    `npm run <name>` through `package.json` (following aliases of aliases).
- New writer tests (20) and retirement tests (6) cover deterministic-key derivation,
  upsert idempotency, the ownership filter, the "no implicit delete" property, and that a
  default/`--dry-run` run writes nothing (same stubbed-client technique as the
  `seva-maintenance` purge test).
- The retirement test also asserts the shell forms that could run the writer
  (`$( … )`, `bash -c`, `eval`, `sudo sh -c`) are recognised, with a non-vacuity control
  so a detector that matches nothing cannot pass.
- **Assert against the golden files already in the repository.** `data/exports/` holds
  `supabase-events-2026.json`, `supabase-events-2027.json` and `supabase-events-all.json`
  (38 rows across 2026–2027) in exactly the row shape this writer must produce. The
  writer's `start_date`/`end_date` form matches them. Several fields in those files carry
  the **strings** `"None"`/`"True"`/`"False"`; that artefact is not reproduced.
- **Retired the false premise:** the tests assert the key form the code actually uses
  (`${guru.id}-${year}`), not the `generated-<year>-<slug>` string from §4.

## 4. Explicitly out of scope

- No production migration, production write, scheduled run, destructive operation or
  raw production export.
- No schema, RLS, credential or application-behaviour change in this PR.
- No change to `services/aaradhane.service.ts` (it does not read `events`) and no
  change to the readers. **The reader surface is split three ways and one branch is
  already broken**: 15 files read Supabase through `services/event.service.ts` using the
  **anon** key against a **deny-all** RLS table, and `getEvents()` swallows the error and
  returns `[]` — so the public events list, the homepage strip, the admin events table
  and the event detail page read nothing today. The remaining readers use the Firebase
  SDK directly. The `events` `SELECT` policy the backlog requires does not exist. All of
  this is PR-D4c. Readiness review §3; `docs/PR-D4c_READER_CUTOVER.md`.

## 5. Risks

1. **Duplicate rows** if the key omits `guru.id`. With `${guru.id}-${year}` the three
   Raghavendra phases are already distinct guru IDs, so this cannot happen — but a
   "helpful" prefix or suffix would re-introduce it (§3.1).
2. **Silent no-write** if the reader cutover is assumed but only the writer moved —
   the public page reads `aaradhane`/`aaradhanes`, not `events`, so the writer change
   alone is invisible to the public site. Confirm which reader each consumer uses
   before retiring Firestore.
3. **Schema change** (`date` columns, plus `auto_generated`/`year` for ownership) needs
   its own reviewed migration and a back-fill decision for any existing rows.
4. **Default-flip** (`--apply` required) changes CLI behaviour; any other caller of
   `generate-aaradhane.ts` must be found first.
5. **First-tick write** if the scheduled path is enabled in the same change that
   introduces the writer.
