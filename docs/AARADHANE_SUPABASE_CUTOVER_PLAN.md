# Aaradhane scheduled writer — Supabase cutover plan (PR-D4)

Status: **PLAN ONLY — not implemented.** No code, workflow, schema, credential or
production change is made by this document. Production migration status stays
**HOLD** until source-data reconciliation and the remaining migration decisions are
resolved.

Backlog items covered: **B-1** (retire/re-point the scheduled Firestore writer),
**D-4** (Aaradhane writer → Supabase upsert). See
`docs/FIRESTORE_SUPABASE_MIGRATION_BACKLOG.md`.

## 1. Why this is a separate, destructive-adjacent problem

`.github/workflows/aaradhane.yml` writes to the Firestore **`events`** collection on a
schedule, and it does so **by default**:

- `workflow_dispatch` declares `dry_run` with `default: false` (lines 15–19).
- On a `schedule` run `inputs.dry_run` is **empty**, so the live step's guard
  `if: inputs.dry_run != 'true' && steps.check_panchanga.outputs.exists == 'true'`
  (line 254) is satisfied and the step at line 269 runs
  `scripts/generate-aaradhane.ts --year $TARGET_YEAR` **without `--dry-run`**.
- `--firestore` in `scripts/generate-aaradhane.ts` only selects the **read** source
  (Firestore `guruParampara` vs the local file). It does not gate the write. The write
  happens on any run that omits `--dry-run` (`scripts/generate-aaradhane.ts:230-235`).

So the workflow is a **scheduled database writer with no destination guard**, and
`events` cannot be cut over by migrating rows alone: the workflow must be retired or
re-pointed. This is why the cutover is its own change and not part of PR-A2.

### 2.1 Correction to the existing backlog

`docs/FIRESTORE_SUPABASE_MIGRATION_BACKLOG.md` §1.1 states the writer uses
"deterministic IDs `generated-<year>-<slug>`" and that "all writes are idempotent by
ID for a given year", and §4 repeats the same key form. **The code does not do this** —
creates use a random auto-ID and updates rely on a heuristic match. The
`generated-<year>-<slug>` form is a *proposal*, not current behaviour. §1.1 has been
corrected in this change; §4 is retained as the proposal it is.

## 3. Design

### 3.1 Deterministic IDs

Write `events.firestore_id = \`generated-${year}-${guru.id}\`` (the existing
`eventKey`, `generator.ts:211`). `guru.id` is a stable slug (`data/aaradhane/gurus.ts`,
e.g. `madhvacharya`), so the key is stable across runs. This is what makes an upsert
idempotent: a re-run updates the same row instead of inserting a duplicate.

Sri Raghavendra has more than one Aaradhane phase per year. The phase **must** be part
of the key, not a heuristic:

```
generated-<year>-<guruId>            // gurus without phases
generated-<year>-<guruId>-<phase>    // e.g. -aradhana / -punyaradhane
```

Leaving the phase out would collapse two distinct events onto one row. The exact phase
labels come from the existing `raghavendraPhase` values in `generator.ts`.

### 3.2 Idempotent upsert

`upsert(rows, { onConflict: "firestore_id" })`, reusing the repository's established
shape (`scripts/migrate-events-to-supabase-from-json.ts:28-30`,
`lib/supabase/migration-runner.ts:142,150-154`): batch upsert first, then a
**row-by-row retry** if the batch fails, so one bad row does not lose the year.

Two guards the existing precedent does not have and this path needs:

1. **Ownership.** Only rows whose `firestore_id` starts with `generated-` may be
   written, and the payload must carry `auto_generated`/`year`. Without this, a future
   row could collide with a manually curated event.
2. **Deletion policy.** A re-run must never delete rows it did not generate. If the
   expected set for a year shrinks, the stale generated rows must be left alone or
   removed by an explicit, separately authorised step — never by an implicit "delete
   rows not in this batch".

### 3.3 IST date handling

Aaradhane dates are **Indian civil dates**. The correct representation is a plain
`date` (`2027-04-16`), not an instant.

The `events` table currently has `start_date timestamptz` / `end_date timestamptz`.
Storing an Indian civil date as `timestamptz` at UTC midnight renders as **05:30 IST**
on the same day, and is wrong for any consumer that formats in a non-IST zone. The
multi-day derivation in `lib/aaradhane/panchanga.ts:168-176` round-trips through
`toISOString()` (UTC) at a fixed offset; it is self-consistent for UTC-midnight values
today, but it is fragile and couples the date to the process time zone.

Recommended destination shape (a **schema change**, therefore a separate reviewed
migration — not part of the writer PR):

- Add `start_on date` / `end_on date` columns for civil dates; write the panchanga
  date string directly. Keep the existing `timestamptz` columns for non-Aaradhane
  events that genuinely carry a time.
- Derive the target year in `Asia/Kolkata`, never from a UTC timestamp.

If the owner prefers to avoid a schema change, the fallback is to store UTC midnight
and have every reader format in `Asia/Kolkata`. This is the weaker option: it hides the
civil date inside an instant and will break for any reader that does not know the
convention. The plan assumes the column addition.

### 3.4 Retries

No generic retry helper exists in the repo (only `scripts/seva/seed-demo-data.ts:1269
retryingRpc`, and the row-by-row fallback above). Reuse the batch-then-row-by-row
pattern rather than inventing a second retry mechanism. Add bounded retry with backoff
for transient network/5xx errors only, and fail the job loudly on a non-empty expected
set that produced zero rows (the backlog's monitoring note, §4).

### 3.5 Explicit dry-run protection

The current default is dangerous: absence of a flag means *write*. Invert it.

- The writer must require an explicit `--apply` (or equivalent) to write. A run with no
  flag computes and reports, and writes nothing.
- `scripts/generate-aaradhane.ts` keeps `--dry-run` for compatibility, but `--dry-run`
  and the new "no flag" path must both be non-writing.
- The workflow's live step must pass the explicit write flag; a `schedule` run must
  **not** reach the writer at all until the cutover is deliberately enabled.

### 3.6 Workflow re-point (the B-1 part)

The cutover PR must, in one change:

1. Remove the Firestore write (`updateFirestoreWithAdmin`) and the
   `firebase-admin-key.json` materialisation step.
2. Point the live step at the Supabase writer.
3. Add the canonical destination guard **before the first connection or write** —
   reuse `scripts/lib/guard-approved-supabase-url.mjs` (the same guard the two
   Firestore migration workflows use); do not create a new guard.
4. Add `environment: production` to the job, matching the other write-capable jobs.
5. Add a `concurrency` group so two runs cannot interleave.
6. Keep the schedule, but make the scheduled path non-writing until the owner enables
   it, so the cutover cannot write to production on its first tick by accident.

### 3.7 Inventory / test coverage

- `tests/unit/workflow-writer-inventory.ts` deliberately excludes Firestore-only
  writers (`DB_SIGNALS` is Postgres-specific, lines 553-560). Once the Aaradhane writer
  targets Supabase it **becomes** a Postgres writer and must be added to
  `DB_WRITER_INVENTORY`, so the completeness check enumerates it.
- New tests: deterministic-key derivation (including the phase suffix); upsert
  idempotency (running twice yields the same rows); IST date derivation across a
  DST-free year boundary; the ownership filter; the "no implicit delete" property; and
  a behavioral test that a default/`--dry-run` run writes nothing (same stubbed-client
  technique as the `seva-maintenance` purge test).
- **Retire the false premise:** the plan's tests must assert the key form the code
  actually uses, not the `generated-<year>-<slug>` string from §4.

## 4. Explicitly out of scope

- No production migration, production write, scheduled run, destructive operation or
  raw production export.
- No schema, RLS, credential or application-behaviour change in this PR.
- No change to `services/aaradhane.service.ts` (it does not read `events`) and no
  change to the admin/stats readers, which still use the Firebase client SDK. Their
  cutover is a **separate** decision and must not be bundled here.

## 5. Risks

1. **Duplicate rows** if the phase is omitted from the key (two phases → one row).
2. **Silent no-write** if the reader cutover is assumed but only the writer moved —
   the public page reads `aaradhane`/`aaradhanes`, not `events`, so the writer change
   alone is invisible to the public site. Confirm which reader each consumer uses
   before retiring Firestore.
3. **Schema change** (`date` columns) needs its own reviewed migration and a
   back-fill decision for any existing rows.
4. **Default-flip** (`--apply` required) changes CLI behaviour; any other caller of
   `generate-aaradhane.ts` must be found first.
5. **First-tick write** if the scheduled path is enabled in the same change that
   introduces the writer.

## 6. Owner actions required

- Decide the phase-key form (read the real `raghavendraPhase` values and approve the
  suffix).
- Approve the `date`-column migration and the back-fill policy for existing rows.
- Confirm the reader cutover sequence, or accept that the writer moves while readers
  stay on Firebase for one cycle.
- Confirm whether the cron stays enabled-but-non-writing, or is disabled until a
  manual first run.
- Reconcile the generated expected count for the target year against the destination
  before retiring Firestore.

## 7. Proposed PR sequence

1. **PR-D4a** — writer: deterministic keys, idempotent upsert, ownership filter,
   explicit `--apply`, IST `date` handling, unit + behavioral tests. Firestore writer
   left in place, Supabase writer **not** enabled in the workflow.
2. **PR-D4b** — workflow re-point: guard, `environment: production`, `concurrency`,
   scheduled path non-writing, Firestore writer and credential step removed.
3. **PR-D4c** (separate) — reader cutover and Firestore retirement, after
   reconciliation.

No step may be merged while production migration status is HOLD.
