# Panchanga and Aaradhane Storage Data Flows

**Status:** implemented, production publication disabled pending owner approval.

This document describes the Supabase Storage replacement for the daily
Panchanga pull-request workflow and the local-directory Aaradhane generation.

## 1. Storage layout

The existing bucket is reused. No bucket or policy is created or changed.

| Object | Purpose |
|--------|---------|
| `Data_flows/Panchanga/current.json` | Latest validated daily record |
| `Data_flows/Panchanga/daily/YYYY-MM-DD.json` | Historical daily record |
| `Data_flows/Panchanga/years/YYYY.json` | Complete yearly dataset |
| `Data_flows/Aaradhane/current.json` | Most recently published generated dataset |
| `Data_flows/Aaradhane/years/YYYY.json` | Generated Aaradhane events for a year |
| `Data_flows/Aaradhane/snapshots/YYYY/<generated-at>.json` | Previous yearly dataset preserved before replacement |

The Panchanga and Aaradhane folders are independent. Aaradhane generation reads
`Data_flows/Panchanga/years/YYYY.json` and writes only under
`Data_flows/Aaradhane/`.

## 2. Schemas

The full Panchanga record is preserved. `lib/data-flows/schemas.ts` validates:

- `metadata` (`generator`, `version`, `generated_at`, `valid_for`, `timezone`)
- `date`, `location`, `weekday`, `sun`
- `tithi`, `nakshatra`, `yoga`, `karana`
- `masa`, `samvat`
- `rahu_kalam`, `yama_gandam`, `gulika_kalam`, `abhijit_muhurat`
- `durmuhurta`, `varjyam`, `amrita_kalam`

Cross-field rules:

- `metadata.valid_for === date`
- `metadata.timezone === location.timezone === "Asia/Kolkata"`
- astronomical timestamps carry an offset (the naive `metadata.generated_at`
  marker is the only timestamp allowed without one)
- every time value is an ISO 8601 timestamp
- a historical yearly dataset must contain exactly one record for every calendar
  date in its year, including 29 February in leap years

`validatePanchangaYearDataset` accepts a partial year because the daily publisher
builds the current year incrementally. `validateCompletePanchangaYear` adds the
full-coverage rule and is used by bulk imports and historical publication. A
missing day is a hard error; no placeholder or inferred astronomical value is
inserted.

A yearly Panchanga dataset is:

```json
{
  "metadata": {
    "generator": "Rayara Panchanga Engine",
    "version": "1.0.0",
    "generated_at": "2026-11-24T00:00:00+05:30",
    "timezone": "Asia/Kolkata",
    "year": 2026,
    "count": 365
  },
  "year": 2026,
  "days": { "2026-01-01": { "...": "full Panchanga record" } }
}
```

A generated Aaradhane dataset is:

```json
{
  "metadata": {
    "generator": "Aaradhane Generator",
    "version": "1.0.0",
    "generated_at": "2026-11-24T00:00:00+05:30",
    "timezone": "Asia/Kolkata",
    "year": 2027,
    "eventCount": 19,
    "panchangaObjectPath": "Data_flows/Panchanga/years/2027.json"
  },
  "year": 2027,
  "events": [{ "eventKey": "...", "title": "...", "guru": "...", "...": "..." }]
}
```

Aaradhane event fields preserved: `eventKey`, `title`, `description`, `guru`,
`category`, `date`, `endDate`, `allDay`, `featured`, `published`,
`autoGenerated`, `year`, `paramparaNumber`, `raghavendraPhase`,
`lunarCalendar`, `importance`, plus optional `rituals`, `offerings`,
`significance` and `guruName`.

Validation rejects duplicate `eventKey` values, event dates outside the dataset
year, an `endDate` before `date`, and a missing `Poorva`/`Madhya`/`Uttara`
Raghavendra phase when Raghavendra events are present.

## 3. Publication order and safety

`publishPanchangaRecord`:

1. Validates the record against its Asia/Kolkata date.
2. Reads and validates the existing yearly dataset. If it is present but invalid,
   the run stops before writing anything.
3. Writes `daily/YYYY-MM-DD.json` and reads it back.
4. Merges the record into `years/YYYY.json`, writes it and reads it back.
5. Writes `current.json` last.

A failure at steps 2–4 leaves the previous `current.json` untouched, so a failed
generation or upload cannot replace the last known-good day. `current.json` is
never written before the daily record has been verified.

`publishAaradhaneYearDataset`:

1. Validates the complete dataset.
2. Refuses to overwrite an existing yearly dataset that is invalid.
3. If a valid previous dataset exists and differs, writes it to
   `snapshots/YYYY/<generated-at>.json` first. An existing snapshot must be
   readable and identical to that previous dataset; otherwise publication stops
   before the yearly object is replaced.
4. Writes the new yearly dataset and verifies it.
5. Advances `current.json` only when `advanceCurrent: true` is passed.

`current.json` is intentionally not updated by default. Regenerating a historical
year replaces only `years/YYYY.json` and its snapshot, so an old year cannot
become the current dataset by accident. The scheduled Aaradhane workflow passes
`--advance-current`; a manual run must set `advance_current: true` and
`dry_run: false`. The historical import tool always passes
`advanceCurrent: false`.

`publishPanchangaYearDataset` (the historical import path) preflights every daily
object and the yearly object before the first write. It aborts with zero writes
if any existing object has different content, invalid JSON or an unreadable
response. Missing or identical objects proceed. It also defaults to
`requireCompleteYear: true`, so it rejects a year with any missing date, an
invalid date, a key/record mismatch, an out-of-year record, or a duplicate record
before writing the first object. Partial bulk copies require an explicit
`requireCompleteYear: false` and are not used by the import tool.

All writes are upserts on a fixed object key, and verification compares the
read-back payload with the intended payload after every write.

## 4. Readers

Server entry point: `lib/data-flows/server.ts` (imports `server-only`).

| Function | Object |
|----------|--------|
| `getCurrentPanchanga()` | `Panchanga/current.json` |
| `getDailyPanchanga(date)` | `Panchanga/daily/YYYY-MM-DD.json` |
| `getYearlyPanchanga(year)` | `Panchanga/years/YYYY.json` |
| `getCurrentAaradhaneDataset()` | `Aaradhane/current.json` |
| `getAaradhaneYearDataset(year)` | `Aaradhane/years/YYYY.json` |

`getCurrentPanchanga` returns `status: "ok" | "stale" | "unavailable"`. A stale
record is a valid last publication from another IST day; it is never labelled
current. An unavailable result contains no fabricated astronomical data.

The home widget and digital-signage board render an explicit unavailable state
instead of yesterday's record or CMS/temple-timing values. Raya AI only reuses a
cached record when the cache key matches the requested IST date; a failed Storage
read never promotes a previous day's cache to today.

Public HTTP routes:

- `GET /api/panchanga/current` — `no-store`
- `GET /api/panchanga/daily/[date]` — controlled cache
- `GET /api/panchanga/years/[year]` — controlled cache
- `GET /api/aaradhane/datasets/current` — `no-store`
- `GET /api/aaradhane/datasets/[year]` — controlled cache

The browser never reads Storage directly and never receives the service-role key.

## 5. Workflows

### Panchanga (`panchanga.yml`)

Runs on the four existing schedules. It computes the date with
`TZ=Asia/Kolkata`, generates to an artifact, validates without writing, and only
publishes when the repository variable
`PANCHANGA_STORAGE_PUBLISH_ENABLED=true`. It creates no PR and requests no
auto-merge.

### Aaradhane (`aaradhane.yml`)

The existing generation job reads the yearly Panchanga from Storage and previews
the events. A separate `publish-aaradhane` job is gated as follows:

- scheduled run: `AARADHANE_STORAGE_PUBLISH_ENABLED=true`
- manual run: `AARADHANE_STORAGE_PUBLISH_ENABLED=true` **and** `dry_run: false`

`dry_run` defaults to `true`, so a manual dispatch cannot publish by accident.
The publish job repeats the manual check in a refusal step before the write
command as defense in depth. No step passes `--apply`; the database write path is
not used.

`current.json` advance rules:

- scheduled run: allowed, because it publishes the automatically computed
  next-year dataset; the step passes `--advance-current`.
- manual run: only when `advance_current: true` **and** `dry_run: false`.
- historical year regeneration: `advance_current` must remain `false`; the
  publisher then changes only `years/YYYY.json` and its snapshot.

Both workflows run the shared `scripts/lib/guard-approved-supabase-url.mjs` guard
before reaching the approved project.

## 7. Historical migration

`scripts/migrate-data-flows-to-storage.ts` validates the local historical data
before any upload:

- normalises only `metadata.valid_for` and `metadata.timezone` in records that
  predate those fields;
- validates every daily record against its filename;
- reports duplicate dates, missing days and the first/last date per year;
- rejects the year when any calendar date is missing, including 29 February in a
  leap year;
- rejects invalid dates, day-key/record mismatches and out-of-year records;
- regenerates each Aaradhane year from the validated Panchanga dataset;
- validates every generated Aaradhane dataset.

An incomplete year is a validation failure even in dry-run mode: the process exits
non-zero, the yearly dataset is not used for Aaradhane generation, and the
publication branch refuses to write. Nothing fills the missing astronomical
records.

Upload requires all three of `--publish`, `--confirm-production` and
`DATA_FLOWS_HISTORICAL_UPLOAD_APPROVED=true`. Existing objects with different
content are refused rather than overwritten.

The supported way to run the import in CI is the manual workflow
`.github/workflows/data-flows-historical-import.yml`:

- `workflow_dispatch` only, bound to the `production` environment, and only from
  `main`;
- requires the dispatch input `confirm_production` to equal exactly
  `publish-historical-data-flows`;
- maps `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from the
  repository secrets (names only, never printed), runs
  `scripts/lib/guard-approved-supabase-url.mjs` before the write, and sets
  `DATA_FLOWS_HISTORICAL_UPLOAD_APPROVED=true` on the publish step only;
- uploads `artifacts/data-flows/historical-import-report.json` and the combined
  run log as an artifact, including when the import fails.

The import is effectively one-shot per year: after a successful publish, a re-run
stops in preflight on the yearly object ("already exists with different content")
rather than overwriting it.

## 9. Production cutover sequence

No production object was written while implementing this change. The bucket was
inspected read-only (`RayaramathaYNK`, existing `Data_flows/Panchanga` and
`Data_flows/Aaradhane` prefixes empty at inspection time).

The application no longer reads `data/panchanga/**` or
`public/data/panchanga/**` at runtime. The static files are retained only as
repository history/rollback material; they are not a runtime fallback. Because
`current.json` is absent until the first publication, the API correctly reports
unavailable during the import window.

The owner must approve each write step. The safe order is:

1. **Read-only preflight.** Confirm `NEXT_PUBLIC_SUPABASE_URL` points at the
   project that owns the existing `RayaramathaYNK` bucket, then list
   `Data_flows/Panchanga` and `Data_flows/Aaradhane` without writing.
2. **Historical dry run.** Run
   `npx tsx scripts/migrate-data-flows-to-storage.ts` and require exit code `0`,
   `missingDays=0` for every year, complete normal/leap-year coverage, and valid
   Aaradhane datasets. Any missing, invalid, duplicate or out-of-year record
   stops here.
3. **Approve historical import.** Set
   `DATA_FLOWS_HISTORICAL_UPLOAD_APPROVED=true` only after reviewing the dry-run
   report, then run with `--publish --confirm-production` — locally, or through
   the `Import Historical Data Flows to Storage` workflow with
   `confirm_production: publish-historical-data-flows`. This writes yearly
   Panchanga objects, daily Panchanga objects and yearly Aaradhane objects. It
   does not advance either `current.json`.
4. **Verify imported history.** Read back sample daily objects, every yearly
   object, the imports' `metadata.count`, and the Aaradhane `eventCount`. Confirm
   the historical Panchanga paths are exactly `Data_flows/Panchanga/...` and the
   Aaradhane paths exactly `Data_flows/Aaradhane/...`.
5. **Publish current Panchanga.** Run the daily publisher for the current
   `Asia/Kolkata` date, or enable `PANCHANGA_STORAGE_PUBLISH_ENABLED=true` and let
   the scheduled publisher run. Verify `/api/panchanga/current` returns
   `status: "ok"` with `record.date` equal to today's IST date, then verify
   `/api/panchanga/daily/<date>`.
6. **Publish Aaradhane.** Enable `AARADHANE_STORAGE_PUBLISH_ENABLED=true` only
   after approval, then run a manual dispatch with `dry_run: false` (or the
   scheduled January run). Set `advance_current: true` only when the published
   year should become `/api/aaradhane/datasets/current`; leave it `false` for a
   historical year. Verify `/api/aaradhane/datasets/<year>` and, when advanced,
   `/api/aaradhane/datasets/current`.
7. **Reader cutover verification.** Load the home widget, digital-signage page
   and a Raya AI Panchanga question. Each must show live data for the current IST
   date; force an unavailable Storage read and confirm they show the explicit
   unavailable state, not yesterday's data.
8. **Remove static data.** Only after step 7 passes in production. Until then the
   static files stay in the repository untouched.

Rollback before step 8 is a redeploy of the previous application revision. After
step 8, rollback requires restoring the static files from git history. No
production bucket, policy, secret, database record or workflow is changed by this
document.
