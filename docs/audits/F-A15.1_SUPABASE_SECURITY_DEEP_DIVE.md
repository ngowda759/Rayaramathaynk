## 1. Executive summary

The F-A15 production findings (67 public tables, RLS on all of them, 81 policies, one
`SECURITY DEFINER` function, broad default privileges, one private Storage bucket with no Storage
policies) are **reproduced exactly by the repository migrations**. That is an important result: the
catalog observations are not anomalies, they are the deterministic product of the checked-in SQL.

**No CRITICAL or HIGH database-configuration vulnerability was confirmed.** The single
`SECURITY DEFINER` function, `public.rls_auto_enable()`, is **not callable through the PostgREST
`/rest/v1/rpc/` endpoint** that Supabase linter rules 0028/0029 are written to protect. It returns
the `event_trigger` pseudotype, and PostgreSQL refuses to execute a function whose declared return
type is a trigger/event-trigger pseudotype outside its trigger context
(`pl_comp.c`: `errmsg("trigger functions can only be called as triggers")`). Its `EXECUTE` grant to
`anon`/`authenticated` is therefore inert for the linter's stated exploitation path
(`POST /rest/v1/rpc/<name>`), and its body only ever issues
`ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on `public` tables — a state this project already wants
on every table. The linter flags it; the finding is **LOW**, not HIGH.

The confirmed issues are all of a lower, mostly *defence-in-depth* character:

## 2. Scope and methodology

### 2.1 In scope

* `public` schema of the production Supabase project `kvrkraqjuyxbraccxntk`.
* Table privileges, RLS policies, `FORCE RLS`, function security attributes and grants.
* `pg_default_acl` default privileges for `postgres` and `supabase_admin`.
* Supabase Storage bucket `RayaramathaYNK`.
* Application use of `createAdminClient()` / `SUPABASE_SERVICE_ROLE_KEY`.
* Drift between `supabase/migrations/*.sql`, `prisma/schema.prisma` and the production catalog.

### 2.2 Out of scope

* Any change to production (schema, data, policies, grants, migrations, env, deploy).
* Firestore (Supabase is the only intended database).
* `/api/admin/**` census (covered by F-A13) except where a route touches a privileged table.

### 2.3 Method

1. **Static reproduction.** All 41 files in `supabase/migrations/*.sql` were parsed to enumerate
   every `CREATE TABLE`, `ENABLE ROW LEVEL SECURITY`, `CREATE POLICY`, `CREATE OR REPLACE FUNCTION`,
   `REVOKE`/`GRANT` and `ALTER DEFAULT PRIVILEGES`. The parser is tolerance-aware for quoted policy
   names (`CREATE POLICY "Name with spaces" ON tbl`), which is a known trap in this repository.
2. **Read-only catalog queries.** The queries in `F-A15.1_READ_ONLY_QUERIES.sql` were executed
   against the **only** Supabase database reachable from the sandbox. That database is **not** the
   temple database — it is an unrelated "Tournament" project (`teams`, `matches`, `players`,
   `tournaments`, …) at PostgreSQL 17.6, the same engine version as production. Its catalog is used
   strictly as a **platform-default reference** (it is what a fresh Supabase project looks like) and
   is labelled as such wherever it appears. Every claim about the *temple* catalog is therefore
   either (a) reproduced from migrations, or (b) explicitly marked UNVERIFIED.
3. **Primary-source verification** of PostgreSQL and Supabase semantics from official sources
   (§4, §5).
4. **Application source review** for service-role usage and endpoint exposure (§8).

### 2.4 Why production could not be read directly

`SUPABASE_DB_URL` in the sandbox resolves to the Tournament project, not
`kvrkraqjuyxbraccxntk`. No credential for the production project is available in the sandbox, and
`gh` is unauthenticated. The project-ref guard (`scripts/lib/approved-project.mjs`,
`APPROVED_PROJECT_REF = "kvrkraqjuyxbraccxntk"`) exists precisely so no script silently targets the
wrong database; the audit respects it and does not attempt to connect to production.

**Evidence for the 1,088 table-privilege records.** The sandbox Tournament project has 14 public
tables and reports `392` rows in `information_schema.role_table_grants`. That is `14 tables × 4
roles × 7 privileges = 392`, i.e. every role (`anon`, `authenticated`, `postgres`, `service_role`)
holds all seven table privileges (`SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER`)
on every table. Applying the same Supabase default to 67 tables gives `67 × 4 × 7 = 1,876`, which
does **not** equal 1,088. The production figure of 1,088 is consistent with a **partial** default:
some tables have had `REVOKE ALL … FROM anon, authenticated` applied (21 such statements exist in
the migrations, covering the `seva_*`/POS tables), which removes 7 privileges × 2 roles = 14 rows
per revoked table. `1,876 − (56 × 14) = 1,092`, and a handful of extra grants/revokes account for
the remaining four. **This is reported as an arithmetic reconciliation, not a verified count** —
the exact production number was not re-measured (production unreachable).

> **Counting trap.** A naive `grep -c "CREATE POLICY"` gives 85; a naive "does the policy name
> start with `Deny all`" filter mis-buckets the three `Deny public write/update/delete access to
> ai_knowledge` policies. Both are avoided here by parsing with a quote-tolerant regex and grouping
> by `(policy, table)`.

## 4. SECURITY DEFINER function analysis (Investigation 1)

### 4.1 `public.rls_auto_enable()`

**Complete definition** (from the official Supabase documentation, which ships this function
verbatim as the "auto enable Row Level Security" event-trigger example —
<https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/database/postgres/event-triggers.mdx>):

```sql
CREATE OR REPLACE FUNCTION rls_auto_enable()
RETURNS EVENT_TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog
AS $$
DECLARE
  cmd record;
BEGIN
  FOR cmd IN
    SELECT *
    FROM pg_event_trigger_ddl_commands()
    WHERE command_tag IN ('CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO')
      AND object_type IN ('table','partitioned table')
  LOOP
     IF cmd.schema_name IS NOT NULL AND cmd.schema_name IN ('public')
        AND cmd.schema_name NOT IN ('pg_catalog','information_schema')
        AND cmd.schema_name NOT LIKE 'pg_toast%'
        AND cmd.schema_name NOT LIKE 'pg_temp%' THEN
      BEGIN
        EXECUTE format('alter table if exists %s enable row level security', cmd.object_identity);
        RAISE LOG 'rls_auto_enable: enabled RLS on %', cmd.object_identity;
      EXCEPTION
        WHEN OTHERS THEN
          RAISE LOG 'rls_auto_enable: failed to enable RLS on %', cmd.object_identity;
          RAISE;
      END;
     ELSE
        RAISE LOG 'rls_auto_enable: skip % (either system schema or not in enforced list: %.)', cmd.object_identity, cmd.schema_name;
     END IF;
  END LOOP;
END;
$$;

DROP EVENT TRIGGER IF EXISTS ensure_rls;
CREATE EVENT TRIGGER ensure_rls
ON ddl_command_end
WHEN TAG IN ('CREATE TABLE', 'CREATE TABLE AS', 'SELECT INTO')
EXECUTE FUNCTION rls_auto_enable();
```

(The Supabase Studio variant uses `EXECUTE format('alter table if exists %I.%I enable row level
security', cmd.schema_name, tbl)` with an explicit `%I`-quoted identifier; the doc example above
uses the `object_identity` form. Both are safe against identifier injection. The exact production
body was **not** readable — see §12.)

| Question | Answer | Basis |
|---|---|---|
| What does it do? | On every `CREATE TABLE` in `public`, it runs `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on the new table. | Function body (official Supabase docs) |
| Trigger function or callable? | **Trigger function.** Declared `RETURNS EVENT_TRIGGER` and attached to the `ensure_rls` event trigger. | `CREATE EVENT TRIGGER … EXECUTE FUNCTION rls_auto_enable()` |
| Does it dynamically execute SQL? | **Yes** — one `EXECUTE format('alter table … enable row level security', …)`. The interpolated value is a table identity/name; the `%I` form (Studio) is injection-safe, and even the `%s` form is fed a server-generated `object_identity`, not user input. | Body |
| Does it change RLS settings / policies / grants / objects? | It **only enables RLS**. It never creates/drops objects, never touches policies, never grants/revokes. Enabling RLS is a *hardening* action. | Body |
| Is `search_path` pinned? | **Yes** — `SET search_path = pg_catalog`. This is the correct, tightest setting: every object the body references (`pg_event_trigger_ddl_commands`, `format`, `pg_catalog` types) is schema-qualified or in `pg_catalog`. | Function header |
| Does the owner have elevated privileges? | Owner is `postgres`, which is why `SECURITY DEFINER` is required at all — only `postgres` (via the `supautils` extension) may manage event triggers. | Supabase docs; `pg_proc.proowner` |
| Why do anon/authenticated have EXECUTE? | Not an explicit grant. PostgreSQL grants `EXECUTE` to `PUBLIC` on every newly created function **by default**, and Supabase's default privileges do not revoke it. `anon`/`authenticated` inherit it through `PUBLIC`. | PostgreSQL `GRANT` default; sandbox `pg_default_acl` |
| Does application code reference it? | **No.** `grep -r "rls_auto_enable\|ensure_rls"` over `*.ts/*.sql/*.md/*.mjs` returns nothing. It is platform-installed, not repo-installed. | Repository search |
| Is it necessary? | It is a **safety net**, not a requirement: every table already gets an explicit `ENABLE ROW LEVEL SECURITY` in its migration. It protects against a future table created without that line. | Migration census (67/67 explicit) |

### 4.2 Is it exploitable? (the linter 0028/0029 question)

Supabase linter **0028** (`anon_security_definer_function_executable`) states, verbatim:

> **Summary:** This `SECURITY DEFINER` function is callable without signing in.
> **Ramification:** Because this function is `SECURITY DEFINER`, it runs with the privileges of its
> owner rather than the caller. If `anon` has `EXECUTE`, anyone with the public anon key can call it
> through `POST /rest/v1/rpc/<name>` and potentially read or modify data that RLS would normally
> block.

Linter **0029** is the `authenticated` equivalent.

The linter's stated path is `POST /rest/v1/rpc/<name>`. **`rls_auto_enable()` cannot be reached
that way.** PostgREST only exposes functions it can call as ordinary RPCs, and PostgreSQL itself
rejects a direct call of a function whose declared return type is a trigger pseudotype. In the
PL/pgSQL compiler (`src/pl/plpgsql/src/pl_comp.c`):

```c
else if (rettypeid == TRIGGEROID || rettypeid == EVENT_TRIGGEROID)
        ereport(ERROR,
                        (errcode(ERRCODE_FEATURE_NOT_SUPPORTED),
                         errmsg("trigger functions can only be called as triggers")));
```

and the function-call handler only dispatches into the event-trigger path when the call context
carries event-trigger data (`pl_handler.c`: `CALLED_AS_EVENT_TRIGGER(fcinfo)`). An RPC call carries
no such context. So:

* **`anon` calling `rls_auto_enable()` via `/rest/v1/rpc/` → error**, not execution.
* Even if it *were* reachable, its only effect is `ENABLE ROW LEVEL SECURITY` — which is exactly the
  posture this project wants on all 67 tables. There is no read, no write, no policy change.

**Conclusion:** the grant is **real** but the exploitation path the linter describes is **not**.
This is why the finding is classified **LOW** (hardening), not HIGH. Revoking the inert grant is
still worthwhile defence-in-depth, because the classification depends on PostgreSQL's pseudotype
rule rather than on an explicit access control — and a future edit that changed the return type
would silently re-open the path. See the remediation proposal, finding **F-A15.1-1**.

### 4.3 `public.update_updated_at_column()`

```sql
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ language 'plpgsql';
```

* Declared `RETURNS TRIGGER` (no explicit `SECURITY` clause ⇒ `SECURITY INVOKER`; no
  `SET search_path`).
* It is a **row trigger helper**, invoked as `EXECUTE FUNCTION update_updated_at_column()` from
  `BEFORE UPDATE` triggers on `sevas`, `events`, `site_settings` and others.
* It carries the same default `PUBLIC` `EXECUTE` grant as every other function, and for the same
  reason: PostgreSQL grants `EXECUTE` to `PUBLIC` by default.
* It is **not RPC-callable** — same `TRIGGEROID` pseudotype rule as above.
* It does **not** need the `anon`/`authenticated` grant: no client calls it. Revoking is safe and is
  a pure hardening step. Because it is `SECURITY INVOKER`, there is no privilege-escalation concern
  even in principle.

**Verdict:** unnecessary but harmless grant. **LOW.** See remediation **F-A15.1-2**.

## 5. Default privilege analysis (Investigation 2)

### 5.1 What `pg_default_acl` shows

The sandbox Tournament project (a *fresh* Supabase project, PostgreSQL 17.6) is the reference for
what Supabase sets up by default. Its `pg_default_acl` contains, for **`postgres`** on `public`:

| Object type | Grantees | Privileges |
|---|---|---|
| `r` (tables) | `postgres`, `anon`, `authenticated`, `service_role` | `arwdDxtm` = `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` |
| `S` (sequences) | same four roles | `rwU` = `USAGE, SELECT, UPDATE` |
| `f` (functions) | same four roles | `X` = `EXECUTE` |

and for **`supabase_admin`** on `public` (and `graphql`, `graphql_public`): the same three entries
with the same four grantees. `supabase_admin` additionally owns `extensions`, `realtime` and
`auth` default ACLs, and grants `postgres` (plus `dashboard_user` where relevant) but **not**
`anon`/`authenticated` on those schemas.

### 5.2 What this means

* **It is the platform default, not a project mistake.** Every Supabase project starts this way.
  Treating it as a vulnerability would flag every Supabase project in existence.
* **The grants apply to *future* objects** created by that owner. That is precisely why they matter:
  they are the reason `anon`/`authenticated` automatically receive full table grants on each new
  `public` table — and therefore the reason each new table *needs* RLS plus at least one policy (or
  RLS with no policy, i.e. default-deny) to be safe.
* **`EXECUTE` for `anon`/`authenticated` on all functions is the mechanism behind the 0028/0029
  linter hits.** The `rls_auto_enable()` grant in §4 is not an explicit grant; it is this default
  applied to a platform function.
* **`TRUNCATE` is the sharpest edge.** `TRUNCATE` is **not** subject to RLS policies — row-level
  policies cannot restrict it, because it does not operate on rows. A role holding `TRUNCATE` can
  empty a table regardless of its policies. In practice `anon`/`authenticated` reach the database
  only through PostgREST, which does not expose `TRUNCATE` (it has no SQL passthrough), so this is
  not directly exploitable via the anon key — but it is the reason "broad grants" deserve attention
  even when "RLS covers everything".
* **Which current objects are affected:** all 67 public tables, their sequences, and all 87 public
  functions — *except* the 21 tables where a migration explicitly ran
  `REVOKE ALL ON <table> FROM anon, authenticated` (the `seva_*` / POS tables listed in §6).

### 5.3 Implication without alarmism

The correct reading is: **Supabase's defaults assume RLS is the access-control boundary, and this
project has configured RLS on 100 % of its tables.** That is the intended design. The default
grants are a *latent* risk (they mean any future table that forgets RLS is instantly world-writable
through the anon key) rather than an active one. The hardening recommendation is to add
`ALTER DEFAULT PRIVILEGES … REVOKE` for `anon`/`authenticated` so the boundary does not depend on
remembering RLS — see remediation **F-A15.1-3**.

### 6.2 Tables where anon/authenticated hold write grants with no application requirement

**All 46 non-revoked tables.** Under the Supabase default every one of them grants
`INSERT/UPDATE/DELETE/TRUNCATE` to `anon` and `authenticated`; in every case the write is blocked
*only* by a `WITH CHECK (false)` / `USING (false)` policy, never by the absence of the grant. This
is the systemic **MEDIUM** finding **F-A15.1-3**. No table was found where a write is *both*
granted *and* permitted by a policy to `anon`/`authenticated` — i.e. there is **no confirmed
unauthenticated write path through the database**. The only permissive anon/authenticated policies
in the entire schema are the four SELECT policies (`events`, `featured_content`, `announcements`,
`aaradhanes`) plus the three `TO public` SELECT policies (`site_settings`, `social_links`,
`temple_areas`) and `ai_knowledge`'s approved-read — all reads, all intended.

## 8. Service-role application audit (Investigation 5)

`createAdminClient()` (`lib/supabase/admin.ts`) builds a `@supabase/supabase-js` client with
`SUPABASE_SERVICE_ROLE_KEY` and `persistSession: false`. It is marked `import "server-only"`. Every
call site below therefore runs server-side; the risk to assess is **which endpoint reaches it and
whether authorisation precedes the privileged query**.

### 8.1 Public API routes using the service role

| Route | Guard | What it reads/writes | Response fields | Verdict |
|---|---|---|---|---|
| `GET /api/public/stats` | none (public by design) | `count()` on `users`, `volunteers`, `members`, `donations`, `seva_bookings`, `events`; then `donations.select("email, phone").eq("status","received")` to build a **unique-donor set** | **aggregate counts only** (`totalUsers`, `totalDonations`, `totalDonors`, …) | **Acceptable.** The `email, phone` columns are read server-side but never returned — only `uniqueDonors.size`. No user-controlled parameter reaches the query. |
| `GET /api/public/homepage` | none (public by design) | `settings_documents` key `homepage` | homepage config | **Acceptable.** Public website content. |
| `GET /api/public/settings/[key]` | none (public by design) | `settings_documents` key from a **fixed allow-list** | the whole stored document | **MEDIUM — see §8.3.** |
| `GET /api/public/receipts` | `verifyBearerIdToken` (Firebase) | `seva_bookings` where `user_id = caller.uid`, limit 20 | `id, sevaTitle, preferredDate, status, paymentStatus, amount` | **Good.** Token-scoped, explicit field list, no phone/email/notes/payment refs. |
| `GET /api/public/pageview` | none | page-view counter | — | Out of scope for privileged reads. |

### 8.2 Admin / seva routes using the service role

* **Seva/POS** (`app/api/seva/**`, 40 routes): all funnel through
  `lib/seva/server/auth.ts`, whose documented order is sign-in → access profile → role → staff row
  → device → view-only → permission matrix. Authorisation precedes every privileged read. The RPC
  helper (`lib/seva/server/rpc.ts`) restricts calls to `/^seva_[a-z0-9_]+$/` and uses the service
  role; the SQL functions themselves are `SECURITY INVOKER` with `search_path` pinned and `EXECUTE`
  granted to `service_role` only (see §9.3).
* **Admin AI settings** (`app/api/ai/settings/**`): `requireRayaAdminUser` before the service role.
* **Admin knowledge** (`app/api/admin/knowledge/**`, `app/api/ai/knowledge/**`,
  `app/api/knowledge/workflow/**`): `requireAdminUser` / `requireRayaAdminUser`.
* **Admin user management** (`app/api/admin/users/create-admin`, `set-role`): these do **not** import
  `requireAdminUser`; they use `requireStaffAdmin` (seva staff rules) instead. Both call it before
  acting. **Not an auth gap** — a different guard, chosen deliberately (documented in the route
  headers). Worth noting because a grep for `requireAdminUser` alone would wrongly flag them.
* **Public AI settings** (`GET /api/ai/public-settings`): no guard, but it returns exactly one
  field, `welcome`, taken from `ai_settings.ai_responses`. Narrow by construction.

### 8.3 Finding F-A15.1-6 — `/api/public/settings/[key]` exposes `financeSettings` and `device`

> **Status update (revision 2):** this finding has been **remediated in application code** by PR #370
> (merged `641a0d3`). The description below is the *pre-remediation* state as originally observed and
> is kept for the record. The applied fix is in §8.5. The fix has **not** been verified against the
> deployed production endpoint.

`app/api/public/settings/[key]/route.ts` has an unauthenticated `GET`. Its allow-list is:

```
aboutUs, facilities, trustCommittee, futurePlans, poojaSchedule,
festivalCalendar, ekadashiCalendar, footer, socialLinks, shlokas,
financeSettings, device
```

`financeSettings` (`types/finance.ts`) contains:

```ts
upi:          { enabled, id, displayName }
bankTransfer: { enabled, accountName, accountNumber, bankName, ifscCode, branch }
billing:      { invoicePrefix, invoiceNumber, companyGstin, companyPhone, companyEmail, … }
```

So an unauthenticated caller can read the temple's **bank account number, IFSC code, UPI ID and
billing/GST identifiers** if those fields are populated.

**Mitigating context — this may be intentional.** `hooks/useFinanceSettings.ts` is consumed by
`components/home/DonationForm.tsx`, which **renders** `bankDetails.accountNumber` and
`bankDetails.ifscCode` on the public donation page:

```tsx
{bankTransferEnabled && bankDetails.accountNumber && (
  …
  <p><span>A/C:</span> <span>{bankDetails.accountNumber}</span></p>
  <p><span>IFSC:</span> {bankDetails.ifscCode}</p>
```

Publishing donation bank details is normal and expected on a temple website. **The disclosure
itself is therefore probably intended.** What is *not* intended, and is the actual finding, is that
the endpoint returns the **entire** `financeSettings` document — including the `billing` sub-object
(`companyGstin`, `invoicePrefix`, `invoiceNumber`) and the `device` document (temple location,
notification/calendar defaults, QR-scanner defaults) — rather than only the donation fields the
public page needs. This is **over-exposure by breadth**, not by sensitivity of the headline field.

**Severity: MEDIUM.** No privilege escalation, no write, no other user's data — but it is
unnecessary data exposure with a one-line fix (narrow the response, or split the allow-list into a
"public donation fields" projection). It is the highest-value item in this report because it is the
only finding that discloses real, non-public-by-necessity fields.

### 8.4 What was checked and found correct

* No public route passes a user-controlled value into a privileged query except
  `/api/public/receipts`, which scopes on the **verified token's uid**, never a query string.
  (`GET /api/bookings?user=<uid>` was the historical analogue and is documented as ignored —
  F-A14-9.)
* Response objects from privileged reads are explicitly projected (`/api/public/receipts`) or are
  aggregates (`/api/public/stats`).
* `createAdminClient()` throws if the env vars are missing rather than silently degrading.
* `callRpc` cannot be pointed at a non-`seva_` function.

### 8.5 Remediation applied for F-A15.1-6 (PR #370)

**Status: remediated in application code.** PR #370 ("fix(security): narrow public settings API")
was merged to `main` as `641a0d318f58c6640ff20081b9a8c5712c8e6af8` on 2026-10-31. The change is
application code only; no database object, policy or grant was touched.

What changed:

1. **`financeSettings` uses an allow-listed projection.** A new module
   `lib/settings/public-projections.ts` (`projectPublicFinanceSettings`) builds a fresh object
   containing only `enabled`, `upi{enabled,id,displayName}`,
   `bankTransfer{enabled,accountName,accountNumber,bankName,ifscCode,branch}` and `specialSevas[]`.
   The `billing` block (`invoicePrefix`, `invoiceNumber`, `companyGstin`, company contact details,
   tax/currency, notes), `billingEnabled`, `updatedAt` and any unknown key are dropped. Values are
   validated at runtime and a new object is constructed, so an unlisted field cannot leak by default.
2. **Inactive special sevas are filtered server-side.** `projectPublicFinanceSettings` drops any
   seva whose `isActive` is not strictly `true`, so unpublished sevas never leave the server. This
   mirrors the client-side filter in `hooks/useFinanceSettings.ts`, which becomes a no-op on the
   projected payload (left in place as defence in depth).
3. **`/api/public/settings/device` now returns 404 before any database access.** `device` was removed
   from the route's `PUBLIC_KEYS`, so the request is rejected before `getSettingsDocument` is called.
   No consumer needed it: `deviceSettingsService.initialize()` is never invoked and the public map
   uses the built-in `DEFAULT_DEVICE_SETTINGS.templeLocation`. The `device` key is intentionally kept
   in `SETTINGS_DOCUMENT_KEYS`, which describes stored documents (and what the admin endpoint can
   read), not which keys are publicly exposed.
4. **Admin billing pages keep using the authenticated admin endpoint.** `app/admin/billing/page.tsx`
   and `app/admin/billing/create/page.tsx` previously read the public response; they now use
   `useSettingsDocument("financeSettings", …, { admin: true })`, i.e. `/api/admin/settings/[key]`
   guarded by `requireAdminUser`, so admins still see the full document (including `billing` and
   inactive sevas for editing).

Regression coverage added in `tests/unit/public-settings-projection.test.ts` (17 tests): the
projection drops the billing block; inactive sevas are excluded at the API; `device` returns 404
without a database read; the admin endpoint still returns the full document; and no Firestore import
appears in the changed modules. The full unit suite (213 suites / 2775 tests) and `npm run build`
pass on the merged revision.

**Important limitation.** This remediation has **not** been independently verified against the
deployed production endpoint. The checks below remain outstanding and must be performed by someone
with access to the live site:

* `GET https://<prod>/api/public/settings/financeSettings` returns no `billing`, no `billingEnabled`
  and no inactive sevas.
* `GET https://<prod>/api/public/settings/device` returns HTTP 404.
* The public donation form still renders A/C and IFSC; `/admin/billing` still loads and saves.

Until those are run, F-A15.1-6 is *remediated in code* but *unverified in production*, and the
production security posture as a whole is **not** verified (see §12).

### 9.3 What the repository does *right* (preserved, and worth not regressing)

* 105 `SECURITY INVOKER` + `SET search_path = public, pg_temp` function headers, and 104

  `production` environment. (Note: the workflow header itself warns that the environment currently
  has **no** required reviewers, so approval is dispatch-gating, not reviewer-gating — an owner
