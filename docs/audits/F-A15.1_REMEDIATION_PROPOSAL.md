# F-A15.1 — Remediation Proposal

**Companion to:** `F-A15.1_SUPABASE_SECURITY_DEEP_DIVE.md`
**Date:** 2026-10-31
**Status:** Proposal only. **Nothing in this file has been executed.** No SQL below was run against
any database; no code below was applied.

Every finding carries an explicit **Production approval required** flag. Findings marked *yes*
change the production catalog (grants/policies) and must go through the guarded
`supabase-migrations.yml` workflow (dispatch-only, project-ref-guarded, confirmation-phrase-guarded)
with an owner's approval — and, per the workflow's own header, after required reviewers are enabled
on the `production` environment.

> **Severity is repeated from the deep-dive and is deliberately conservative.** A finding is not
> raised to HIGH merely because a grant exists; effective access (grant ∩ policy ∩ reachability)
> decides the rating.

## F-A15.1-1 — `rls_auto_enable()` `SECURITY DEFINER` with `EXECUTE` for `anon`/`authenticated`

| Field | Value |
|---|---|
| **Severity** | LOW |
| **Root cause** | PostgreSQL grants `EXECUTE` to `PUBLIC` on every new function by default; Supabase's default privileges do not revoke it. The function is `SECURITY DEFINER` because only `postgres` may manage event triggers. |
| **Affected objects** | `public.rls_auto_enable()` (owner `postgres`), event trigger `ensure_rls`. |
| **Affected files** | None in the repository — the function is platform-installed. Any fix must live in a new migration. |

**Proposed remediation.** Revoke the inert `EXECUTE` grant so the access-control boundary does not
rest on PostgreSQL's pseudotype rule. The function is still callable by the event trigger because
event-trigger invocation does not go through the `EXECUTE` privilege check in the same way — but
**verify this in a staging project before production**, because the event trigger must keep working.
A safer variant is to keep `service_role` and revoke only `PUBLIC`/`anon`/`authenticated`:

```sql
-- Proposed (staging-verify first):
REVOKE EXECUTE ON FUNCTION public.rls_auto_enable() FROM PUBLIC, anon, authenticated;
GRANT  EXECUTE ON FUNCTION public.rls_auto_enable() TO service_role;
```

> **Important caveat.** `rls_auto_enable()` is owned by `postgres` and belongs to the Supabase
> platform's `supautils`-managed surface. If the platform re-asserts its ACL on upgrade, this revoke
> may not persist. Confirm the platform's behaviour in a staging project before relying on it, and
> treat the primary control as "RLS is explicitly enabled in every migration" (which it already is,
> 67/67).

**Exact change:** the two statements above, in a new timestamped migration.

**Potential impact:** none expected for the application (no code calls it). Risk is limited to the
`ensure_rls` event trigger; if the revoke were to disable it, new tables would simply stop being
auto-RLS'd — the existing explicit `ENABLE ROW LEVEL SECURITY` in each migration still covers every
table.

**Rollback:**
```sql
GRANT EXECUTE ON FUNCTION public.rls_auto_enable() TO PUBLIC;
```

**Verification:**
```sql
-- Should return false for anon/authenticated after the change:
SELECT has_function_privilege('anon',          'public.rls_auto_enable()', 'EXECUTE'),
       has_function_privilege('authenticated', 'public.rls_auto_enable()', 'EXECUTE');
-- Event trigger still present and enabled:
SELECT evtname, evtenabled FROM pg_event_trigger WHERE evtname = 'ensure_rls';
-- Functional check in a staging project: create a scratch table and confirm RLS is enabled.
```

**Production approval required:** **Yes.**

## F-A15.1-3 — Broad default grants to `anon`/`authenticated` on all public tables

| Field | Value |
|---|---|
| **Severity** | MEDIUM |
| **Root cause** | Supabase platform default privileges grant `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` on `public` tables to `anon`, `authenticated`, `service_role` (and `postgres`). The application relies entirely on RLS policies to block access. |
| **Affected objects** | All 67 public tables (46 with default grants, 21 already `REVOKE`d), plus future tables. |
| **Affected files** | A new migration; `supabase/migrations/*_seva_privilege_hardening.sql` is the existing precedent for this pattern. |

**Proposed remediation — two parts.**

**(a) Future objects** — stop the defaults applying to new `public` tables:
```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
  ON TABLES FROM anon, authenticated;
```
Run once **as the role that owns the default ACL** (`postgres`). Note `ALTER DEFAULT PRIVILEGES`
affects only objects created afterwards by the *executing* role; confirm which role creates tables
in this project (migrations run as `postgres`).

**(b) Existing objects** — revoke the same privileges on the 46 tables that still carry the default.
Generate the statements from the catalog rather than hand-writing 46 lines:
```sql
-- Generate, do not execute blindly:
SELECT format('REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER ON TABLE public.%I FROM anon, authenticated;', c.relname)
FROM   pg_class c
JOIN   pg_namespace n ON n.oid = c.relnamespace
WHERE  n.nspname = 'public' AND c.relkind IN ('r','p')
ORDER  BY c.relname;
```
Keep `SELECT` granted: the public read paths (`events`, `featured_content`, `announcements`,
`aaradhanes`, `site_settings`, `social_links`, `temple_areas`, `ai_knowledge`) use the anon key and
need `SELECT`; their RLS policies then narrow which rows are visible.

**Exact change:** one new migration with (a) plus the 46 generated `REVOKE`s (or a `DO` block that
loops over the catalog).

**Potential impact:** **the highest-risk change in this proposal.** If any public client path
depends on a write grant that a policy currently permits, it would break. The investigation found
**no** such path (no permissive write policy to anon/auth exists), but the change must be rehearsed
in staging. Also confirm no PostgREST "table is read-only" assumption elsewhere.

**Rollback:**
```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER ON TABLES TO anon, authenticated;
-- and GRANT … ON TABLE public.<t> TO anon, authenticated; for each revoked table.
```

**Verification:**
```sql
SELECT table_name, grantee, privilege_type
FROM   information_schema.role_table_grants
WHERE  table_schema = 'public' AND grantee IN ('anon','authenticated')
ORDER  BY table_name, grantee, privilege_type;
-- Expect only SELECT (and no TRUNCATE) for the 8 public-read tables; nothing else.
-- Functional: anonymous homepage/events/gallery reads still return data; every write path 401/403s.
```

**Production approval required:** **Yes.**

## F-A15.1-4 — `FORCE ROW LEVEL SECURITY` is off on all 67 tables

| Field | Value |
|---|---|
| **Severity** | LOW |
| **Root cause** | RLS is enabled but not forced, so the table owner (`postgres`) bypasses its own policies. Nothing in the application connects as `postgres`, so this is not currently reachable by a client. |
| **Affected objects** | All 67 public tables. |
| **Affected files** | New migration. |

**Proposed remediation** (prioritise the sensitive tables rather than all 67 in one step):
```sql
ALTER TABLE public.donations     FORCE ROW LEVEL SECURITY;
ALTER TABLE public.users         FORCE ROW LEVEL SECURITY;
ALTER TABLE public.profiles      FORCE ROW LEVEL SECURITY;
ALTER TABLE public.staff         FORCE ROW LEVEL SECURITY;
ALTER TABLE public.seva_receipts FORCE ROW LEVEL SECURITY;
-- … extend to the rest once verified.
```

**Exact change:** the statements above (optionally a `DO` block over the catalog).

**Potential impact:** **must be staged.** Migrations and maintenance scripts that run as the table
owner rely on bypassing RLS. Forcing RLS on a table whose owner-run job expects to see all rows will
silently change that job's results. Verify every owner-run script (seeds, backfills, the guarded
migration workflows) before forcing.

**Rollback:**
```sql
ALTER TABLE public.<t> NO FORCE ROW LEVEL SECURITY;
```

**Verification:**
```sql
SELECT relname, relrowsecurity, relforcerowsecurity
FROM   pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE  n.nspname = 'public' AND c.relkind IN ('r','p') ORDER BY relname;
```

**Production approval required:** **Yes.**

## F-A15.1-5 — `seva_list_items` has RLS and no policy

| Field | Value |
|---|---|
| **Severity** | LOW |
| **Root cause** | The table's migration enables RLS but declares no policy, relying on PostgreSQL's default-deny. Safe, but the invariant is implicit. |
| **Affected objects** | `public.seva_list_items`. |
| **Affected files** | The migration that creates `seva_list_items`. |

**Proposed remediation** — make the intent explicit and match the sibling tables:
```sql
DROP POLICY IF EXISTS "Deny all public access to seva_list_items" ON seva_list_items;
CREATE POLICY "Deny all public access to seva_list_items"
    ON seva_list_items FOR ALL TO public USING (false) WITH CHECK (false);
```

**Exact change:** the two statements above, in a new migration.

**Potential impact:** none functionally — default-deny and an explicit `USING (false)` deny the same
rows. The `seva_list_items_guard`/`seva_list_items_get` functions run as `service_role` and are
unaffected.

**Rollback:** `DROP POLICY "Deny all public access to seva_list_items" ON seva_list_items;`
(restores the implicit default-deny).

**Verification:**
```sql
SELECT policyname, cmd, roles, qual, with_check FROM pg_policies
WHERE schemaname='public' AND tablename='seva_list_items';
```

**Production approval required:** **Yes.**

## F-A15.1-6 — `/api/public/settings/[key]` exposes `financeSettings` and `device`

| Field | Value |
|---|---|
| **Severity** | MEDIUM |
| **Root cause** | The unauthenticated route's allow-list includes two documents that contain more than the public page needs. `financeSettings` carries bank account number, IFSC, UPI ID and billing/GST identifiers; `device` carries temple-location and device configuration. The public donation page only needs the donation fields. |
| **Affected objects** | None (database unchanged). |
| **Affected files** | `app/api/public/settings/[key]/route.ts`, `services/settings-document.service.ts`, `hooks/useFinanceSettings.ts`, `hooks/useSettingsDocument.ts`, `lib/device/settings.ts`. |

**Proposed remediation — two options; prefer Option A.**

**Option A (preferred): narrow the response for the sensitive keys.**
In `app/api/public/settings/[key]/route.ts`, after fetching the document, project it for the
public keys instead of returning the whole document:

```ts
// After `const data = await getSettingsDocument(key);`
function publicProjection(key: string, data: unknown) {
  if (!data || typeof data !== "object") return data;
  if (key === "financeSettings") {
    const d = data as Record<string, unknown>;
    return {
      upi: d.upi ?? null,               // public donation channel
      bankTransfer: d.bankTransfer ?? null, // public donation channel
      specialSevas: d.specialSevas ?? [],
      enabled: d.enabled ?? true,
      // billing (companyGstin, invoicePrefix, invoiceNumber…) is deliberately NOT exposed
    };
  }
  if (key === "device") {
    const d = data as Record<string, unknown>;
    return { templeLocation: d.templeLocation ?? null }; // only what a public map needs
  }
  return data;
}
return NextResponse.json({ success: true, data: publicProjection(key, data) });
```

**Option B: split the allow-list** into `PUBLIC_KEYS` (content documents) and
`PUBLIC_FINANCE_FIELDS`/`PUBLIC_DEVICE_FIELDS`, served by dedicated routes. More code; cleaner
boundary long-term.

**Exact change:** the edit to `app/api/public/settings/[key]/route.ts` above (Option A). No
database change.

**Potential impact:** `hooks/useFinanceSettings.ts` reads `settings.upi`, `settings.bankTransfer`,
`settings.specialSevas`, `settings.enabled` — all preserved by the projection. `useSettingsDocument`
for `financeSettings` in the **admin** pages reads through the guarded admin path, not this route, so
admin editing is unaffected. `lib/device/settings.ts` only needs `templeLocation` for the public map;
if it needs more, widen the projection deliberately.

**Rollback:** revert the route edit (git revert).

**Verification:**
* `curl https://<prod>/api/public/settings/financeSettings` → response contains `upi`, `bankTransfer`,
  `specialSevas`, `enabled`, and **no** `billing`.
* The public donation form still renders A/C and IFSC.
* Admin `/admin/billing/settings` and `/admin/settings/finance` still load and save.
* `curl …/api/public/settings/device` → contains only `templeLocation`.
* Add a regression test asserting `billing`/`companyGstin` are absent from the public response.

**Production approval required:** **No** — code-only change, but it is a behaviour change to a public
endpoint, so it should be reviewed and staged like any other.

## F-A15.1-7 — Private Storage bucket `RayaramathaYNK`, no policies

| Field | Value |
|---|---|
| **Severity** | LOW |
| **Root cause** | The bucket was created out of band (no migration), and nothing in the application references Supabase Storage. A private bucket with no policies is fail-closed. |
| **Affected objects** | `storage.buckets` row `RayaramathaYNK`; `storage.objects`. |
| **Affected files** | None. |

**Proposed remediation — owner decision required:**
* **If unused (likely):** delete the bucket (owner action in the Supabase dashboard or
  `DELETE FROM storage.buckets WHERE id = 'RayaramathaYNK'` — **destructive; confirm emptiness and
  take a backup first**). Do not run this in the audit.
* **If intended to be used:** create it in a migration and add an explicit policy set (least
  privilege — e.g. service-role-only, matching the deny-all posture of the rest of the schema), and
  wire it into `services/storage.service.ts` (or explicitly document that Vercel Blob is the only
  media store).

**Exact change:** none proposed automatically; this is a decision, not a patch.

**Potential impact:** deleting a non-empty bucket destroys objects. Check
`SELECT count(*) FROM storage.objects WHERE bucket_id = 'RayaramathaYNK';` first.

**Rollback:** bucket deletion is not reversible without a backup.

**Verification:**
```sql
SELECT id, name, public FROM storage.buckets ORDER BY name;
SELECT schemaname, tablename, policyname, cmd FROM pg_policies WHERE schemaname='storage';
```

**Production approval required:** **Yes** (any bucket change).
