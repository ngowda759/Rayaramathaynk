# F-A15.2 — Public Settings Projection (Remediation)

**Finding:** F-A15.1-6 — `GET /api/public/settings/[key]` returns complete `financeSettings`
and `device` documents using a service-role database client.
**Status:** implemented, unmerged (PR pending review).
**Date:** 2026-10-31

---

## 1. Problem

`GET /api/public/settings/[key]` is unauthenticated and reads `settings_documents` with the
service-role client (the table is deny-all under RLS, so the browser cannot read it directly).
For two of its twelve allow-listed keys it serialized the **whole stored document**:

| Key | Over-exposed fields | Public consumer needs |
|-----|--------------------|----------------------|
| `financeSettings` | `billing` (invoice prefix/counter, GSTIN, company name/address/phone/email, tax rate, currency, notes), `billingEnabled`, inactive special sevas, `updatedAt` | `enabled`, `upi`, `bankTransfer`, active `specialSevas` |
| `device` | the whole document (`notificationDefaults`, `calendarDefaults`, `shareTemplates`, `qrScannerDefaults`, `defaultNavigationApp`, `templeLocation`) | nothing — no public consumer reads a stored `device` document |

The donation fields themselves (`upi.id`, `bankTransfer.accountNumber`, `ifscCode`) are
**intended public**: the donation form renders them so devotees can pay. The defect is the
breadth of the response, not the presence of payment details.

## 2. Fix

Two changes to the public endpoint:

1. `financeSettings` is narrowed by a runtime, allow-listed projection.
2. `device` is **removed from the public endpoint entirely** — it returns `404`.

`lib/settings/public-projections.ts` — `projectPublicSettingsDocument(key, data)`:

- `financeSettings` → `{ enabled, upi{enabled,id,displayName}, bankTransfer{enabled,accountName,accountNumber,bankName,ifscCode,branch}, specialSevas[] }`.
  - `specialSevas` is filtered to `isActive === true` **at the API level**, so unpublished
    sevas never leave the server. A missing or non-boolean `isActive` counts as unpublished.
    This matches the client-side filter in `hooks/useFinanceSettings.ts`, which becomes a
    no-op on the projected payload (it is left in place as defence in depth).
- Every other key passes through unchanged.
- Values are validated at runtime (`typeof`/`Number.isFinite`, plain-object checks) and a
  **fresh object is built**, so an unknown or newly-added internal field cannot leak by default.

`app/api/public/settings/[key]/route.ts`:

- Wrap the read result in the projection.
- Remove `"device"` from `PUBLIC_KEYS`, so a request for it is rejected with `404` **before
  the database is touched**. The `device` key is intentionally left in
  `SETTINGS_DOCUMENT_KEYS`: that registry describes the stored documents the application
  knows about (and the admin endpoint reads), not which keys are publicly exposed.

### Backward compatibility

- Public donation components (`DonationCTA`, `DonationForm`, `SevaBooking`) read only the
  projected fields; the projection preserves their shapes exactly. `hooks/useFinanceSettings.ts`
  is unchanged. Its `normalize()` still deep-merges `billing`, but that now falls back to
  `defaultFinanceSettings` on the public path — the same effective value the public site used
  (nothing public read it).
- The `device` removal is safe: `deviceSettingsService.initialize()` was never called, no
  component fetches `/api/public/settings/device`, and the public map uses
  `DEFAULT_DEVICE_SETTINGS.templeLocation` directly.
- The two admin pages that depended on the public response for `billing` were moved to the
  admin-guarded endpoint:
  - `app/admin/billing/page.tsx` — `useFinanceSettings()` → `useSettingsDocument("financeSettings", defaultFinanceSettings, { admin: true })`.
  - `app/admin/billing/create/page.tsx` — same change.
  Both pages already run behind `AdminAuthGuard`, and `/api/admin/settings/[key]` is guarded by
  `requireAdminUser`, so the full document (including `billing` and inactive sevas) remains
  available to admins.
- `lib/device/settings.ts` — removed the dead `fetch("/api/public/settings/device")` from
  `initialize()`, plus two pre-existing unused type imports.

## 3. Verification

- `tests/unit/public-settings-projection.test.ts` (17 tests): projection unit tests including
  the inactive-seva filter and malformed input; public route (finance projection, **device
  → 404 without touching the DB**, content passthrough, missing → `data: null`, unknown key →
  404, 500 on read failure); donation-hook compatibility; admin route still returns the full
  document (billing **and** inactive sevas); unauthorized admin rejected before any read; and
  no Firestore import in the changed modules.
- Full unit suite: **213 suites / 2775 tests pass**.
- `npx tsc --noEmit` clean; `npx eslint` clean on changed files; `npm run build` succeeds
  (264/264 static pages).

## 4. Not in scope

- The stored `device` document still exists in `settings_documents`; it is simply no longer
  served publicly. Removing the row would be a production data change and is out of scope.
- `financeSettings.billingEnabled` is still absent from the public response. No public
  component read it; `hooks/useFinanceSettings` defaults it to `false`.

## 5. Rollback

Revert the commit. The route then serves the whole document again (and `device` again); no
schema, data or configuration change is involved.
