What it is

This is the web platform of the Sri Raghavendra Swamy Matha at Rayara Matha, Yelahanka (13.1005 N, 77.5963 E, Asia/Kolkata). It is one Next.js application serving three audiences at once.

Devotees are the public audience. They arrive to read about the Matha and its guru parampara, check today's panchanga and the festival calendar, browse events and the photo gallery, request a seva, make a donation, look up a receipt, and ask questions of Raya AI, a chat assistant that answers from the temple's own facts rather than from a language model's memory.

Temple administrators — counter clerks, office staff, priests, trustees — use an admin console at /admin to publish events and announcements, curate the gallery, maintain the seva catalogue and the daily pooja timetable, work the booking and donation queues, issue numbered seva receipts, and edit the copy the public site renders.

The trust is the third, indirect audience: the receipt book, the reports screen and the donation ledger exist so the institution can account for what it receives.

Two facts of the temple context shape the whole system. Money is manual — there is no payment gateway anywhere in the repository; a devotee is shown a UPI ID, pays out of band, and types a reference back into the form. And dates are lunar — the Matha's nineteen Guru Aaradhanes fall on lunar tithis, so a Python job computes a full Hindu almanac (panchanga) for the temple's coordinates and commits it into the repository as JSON.

Admin console

A sidebar shell around a dashboard, fourteen settings pages, content and media management, and the devotional-operations back office. A floating chat widget on every page, backed by POST /api/chat, plus an admin console of a hub and eleven sub-pages. Architecture

A browser hits Vercel. Every non-static GET first passes through proxy.ts (Next 16's rename of middleware.ts), which writes a page_views document and sets headers. The request then reaches either a Server Component page — which usually delegates immediately to a client subtree — or a Route Handler. From there the application talks to five external systems through the service layer.

Solid lines are the intended path. The dashed line is the leak: 41 files in app/, components/ and hooks/ hold the Firebase client SDK directly and never touch services/.

Two things cross the boundary in the wrong direction, and they explain most of the “it silently does nothing” behaviour. The client Firebase SDK is used inside server Route Handlers, so Firestore rules apply to a request with no signed-in user and the read returns nothing. And server-only SDKs (@vercel/blob, the Supabase service-role client) are imported from "use client" components, so uploads and Site Settings saves throw in a deployed build.

How a request flows

Rendering the home page

  1. app/(public)/page.tsx — Server Component, revalidate = 60.
  2. lib/gallery.ts:21 getTempleGalleryImages() — readdirSync(public/images/temple), returns {image,title,size}[] off the deployment filesystem.
  3. services/daily-spiritual.service.ts getDashboardData() — awaited inside a try/catch; on failure dashboardData stays null and the dashboard section renders nothing.
  4. Both values serialise into <HomeClient galleryImages dashboardData>. From here the tree is client-only.
  5. In the browser Hero mounts; hooks/useHomepage.ts sets defaults on a setTimeout(0) then opens an onSnapshot on Firestore homepage/config. Until the snapshot arrives the hero is a full-height spinner.
  6. Six further independent round-trips fire after hydration: announcements → Firestore; panchanga → fetch("/data/panchanga/current.json"); events → Supabase; recommendations → GET /api/recommendations; testimonials → Firestore; social links → Supabase social_links.

A seva booking write

  1. components/home/SevaBooking.tsx:127 handleSubmitClick() — requires login, a seva and a date, and nothing else.
  2. :146 handleBooking() — mints a client-side reference SVA-${Date.now().toString(36)} which is never persisted.
  3. services/sevaBooking.service.ts:34 createBooking() — addDoc into Firestore sevaBookings with status: "pending", using the client SDK, from the browser.
  4. SevaBooking.tsx:114 — the UPI payee comes from hooks/useFinanceSettings.ts:22 (a direct getDoc, no service), falling back to a hardcoded literal. The devotee pays in their own UPI app and types the reference back.
  5. :181 handleSavePaymentReference() → services/sevaBooking.service.ts:81 updatePayment() — sets paymentStatus: "completed", status: "confirmed". No server participates, and nothing verifies the transaction.
  6. Read-back: :55 queries where userId == + orderBy createdAt, for which the declared index is userId + preferredDate — the query throws FAILED_PRECONDITION.
  7. Public lookup: app/api/public/receipts/route.ts:19 reads the newest 1000 sevaBookings with the Admin handle and substring-matches phone/email — unauthenticated, returns PII.
  8. The booking surfaces in /admin/bookings and /admin/seva-bookings for manual reconciliation.

One Raya AI chat message

  1. components/ai/AIChatProvider.tsx:156 — POST /api/chat with {messages, sessionId, userId, detectedLanguage}.
  2. app/api/chat/route.ts:80 — checkRateLimit() on x-forwarded-for; in-memory Map, 20 req/60 s. This is the only gate; the route has no auth.
  3. :112,124 — picks the last user message, derives responseLanguage by testing for the Kannada Unicode block.
  4. :143 — getSessionContext() loads Firestore chat_sessions/{id}; if none, :158 mints a UUID.
  5. :162 → lib/ai/generator.ts:1056 generateResponse() → lib/ai/intent/detector.ts:677 detectIntent() → IntentDetector.detect() (:204): out-of-scope guard, keyword match, a “semantic” pass, then combineResults().
  6. Dispatch to one of the generator's 33 case Intent.* handlers — 42 intents, so nine fall through the default branch — e.g. handleTempleTimings() reads Firestore timings then settings, with a 5-minute module cache and a DEFAULT_SETTINGS fallback.
  7. lib/ai/generator.ts:119-138 — formats one of three hardcoded bilingual templates. usesLLM: false on every path.
  8. :183 — updateSession() writes both messages with arrayUnion and prunes to 20. If confidence < 50, the question is written to Firestore unknown_questions.
  9. :304-339 — returns {message, sessionId}, but the returned sessionId is resolvedSessionId || crypto.randomUUID(), not effectiveSessionId, so a first-turn client is handed an id no document uses.

Both user journeys work in outline and break in detail. Step 5 of the seva flow lets anyone mark a booking paid. In the admin event flow, EventForm builds Firestore Timestamp objects and hands them to a Supabase-backed service, and the event detail page calls .toDate() on what Supabase returns as an ISO string, so it throws for every event (app/(public)/events/[id]/page.tsx:63).

Rules and indexes, in one paragraph each

  • Rules. firestore.rules is additive, and both properties bite. match /settings/{docId} is declared twice and the second block allows write: if true, so every settings document is publicly overwritable; ai_settings is world-readable and world-writable. Meanwhile 25 collections the code actively uses have no match block at all — including profiles, bookmarks and all seven knowledge-workflow collections — so those reads and writes are denied and the errors are swallowed into empty UI states. receipts and system are correctly tight.
  • Indexes. firestore.indexes.json declares 22 composite indexes. Six are declared and used. Twelve queries run without the index they need and throw FAILED_PRECONDITION — notably sevaBookings (declared on the wrong second field), announcements (declared on active while the code says isActive), galleryMedia, bills, and all six knowledge-workflow queries.
  • No request-time authorization. The only request-time interceptor is proxy.ts, which writes page_views and sets headers and authorizes nothing; the admin gate is a client-side React guard only.

Consequences worth knowing before touching it: editing the system prompt in the admin console changes nothing; every analytics recorder (token usage, latency, intent distribution) has zero callers, so every AI chart reads an empty collection; unknown questions are written to one store and triaged from two others; three intents share a case label and answer with opening hours regardless of the question; and the 275-case UAT suite asserts only that an intent was detected, never which one.

State of the platform

The site renders, the admin console is navigable, and the Receipt Book genuinely works. Everything else needs qualifying. The platform is mid-migration from Firestore to Supabase and stopped halfway: Supabase owns events, site settings and temple areas; Firestore owns everything else; and two domains — sevas and social links — are read from one store while being written to the other, so an administrator's edits never reach the public page. Nine Supabase tables exist with no application code reading them at all, and several of the tables the code does read are locked to deny-all, so those reads return nothing and the services swallow the error.

Authorization is the second systemic gap: the request-time interceptor proxy.ts authorizes nothing, the admin gate is a client-side React guard, and 88 of the 95 API route files perform no identity check — including routes that mint a super-admin, overwrite AI settings, or return devotee phone numbers.

A third of the code is scaffolding: the entire knowledge-approval workflow (about 2,000 lines) has no reachable UI, the nine device widgets have no consumers, the 825 translated strings are never rendered because no i18n provider is mounted, the LLM provider abstraction is fully written but its only call site is commented out, and several admin screens (/admin/library, /admin/stotras, /admin/calendar/*) persist nothing at all.

Finally, the quality apparatus is decorative: the deploy workflow pushes to production with no lint, typecheck or test step, the Playwright config points at a directory that does not exist, and the no-explicit-any rule the coding standards rest on is switched off for the whole source tree.
