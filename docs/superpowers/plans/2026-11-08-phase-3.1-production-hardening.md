**Date:** 2026-11-08

**Prerequisite:** Phase 3 merged into `main` (`2d0a8485`)  

---

## 1. Objective

Solidify and harden the unified Supabase Auth system in production before undertaking Phase 4 (Firebase removal/cleanup). Specifically:
1. **Secure Registration & Self-Provisioning APIs:** Prevent spoofed registration or phantom profile injection by requiring token verification or Supabase Auth Admin validation on `/api/auth/register`, and handle concurrent insertion races idempotently in `/api/auth/me`.
2. **Mandatory Supabase Auth Identity for Admins:** Enforce that administrative user provisioning (`create-admin` and `set-role`) strictly fails closed if a valid Supabase Auth identity cannot be provisioned or verified.
3. **Production Verification:** Verify live authentication flows (login, registration, password reset, session persistence, staff/counter authorization).
4. **End-to-End Supabase Identity Traversal:** Confirm all ordinary user, devotee, and staff request flows operate with canonical Supabase identities (`public.users.auth_user_id` and `public.staff.auth_user_id`).
5. **Preserved & Instrumented Firebase Fallback:** Keep the non-blocking Firebase fallback intact for zero-lockout compatibility, with structured audit metrics to observe remaining legacy token usage.

## 3. Files to Be Modified

1. **`app/api/auth/register/route.ts`**:
   - Add identity validation: If a Bearer token is present, verify caller owns `userId`. If called during initial sign-up without an active session, verify `userId` against Supabase Auth admin SDK (`admin.getUserById(userId)`) and assert email match.
   - Enforce that `userId` must exist in Supabase Auth before creating a `public.users` devotee record.
   - Handle unique constraint races idempotently (PostgreSQL error `23505`).
2. **`app/api/auth/me/route.ts`**:
   - Harden self-provisioning insert against concurrent request races (duplicate key `23505`), falling back to a safe re-fetch (`maybeSingle()`).
   - Guarantee `auth_user_id` is always prioritized and populated.
3. **`app/api/admin/users/create-admin/route.ts`**:
   - Enforce fail-closed check: if `authUserId` cannot be created or verified in Supabase Auth, throw `SevaError("internal")` and refuse to proceed with `onboardStaff`.
   - Ensure no admin staff row or `public.users` admin role is created without an authoritative Supabase Auth UUID.
4. **`app/api/admin/users/set-role/route.ts`**:
   - When promoting a user to an admin role (`admin` or `super_admin`), ensure the target account has a valid Supabase Auth identity (`auth_user_id`). If the user exists only in legacy Firebase, auto-provision or link their Supabase Auth identity to prevent orphaned admin accounts.
5. **`lib/seva/server/staff.ts`**:
   - In `onboardStaff`, if `input.role` is an admin console role (`super_admin`, `temple_admin`, `admin`), require that `authUserId` is present and valid UUID.
6. **`lib/auth/verify-id-token.ts`**:
   - Add structured telemetry logging whenever the secondary Firebase fallback path is invoked (`[fallback:firebase] token verified for legacy UID`), allowing measurement of legacy session drain without exposing tokens.
7. **`tests/security/auth-hardening.test.ts`** *(New Test Suite)*:
   - Dedicated security and edge-case test suite for registration hardening, admin provisioning enforcement, and race condition handling.

## 4. Impact Analysis

- **Devotee Experience:** Completely transparent. Registration remains smooth and gains protection against concurrent page-load race conditions.
- **Admin Security:** Eliminates any risk of administrative accounts being provisioned with only Firebase credentials, ensuring all new and promoted admins can authenticate via Supabase Auth.
- **Attack Surface Reduction:** Prevents spoofed POST requests to `/api/auth/register` with arbitrary `userId`s.
- **Database / Schema:** Zero database schema changes required. `public.users` and `public.staff` schemas already support `auth_user_id`.
- **Breaking Changes:** None. Firebase fallback remains operational for legacy sessions.

---

## 5. Risks & Mitigation

| Risk | Impact | Mitigation |
|---|---|---|
| Concurrent sign-up / sign-in profile writes | Transient 500 error on `/api/auth/me` | Catch Postgres code `23505` (unique violation) and retry with `maybeSingle()`. |
| Unauthenticated sign-up without active session | Failed registration if token is required | Validate `userId` against Supabase Auth admin API (`getUserById`) when Bearer token is absent. |
| Admin creation partial failure | Orphaned Supabase Auth or staff record | Run validation before writing, throw clean `SevaError("partial_failure")` if database write fails. |
| Legacy Firebase token lockout | Legacy users locked out before cutover | Retain secondary verification path in `verify-id-token.ts` with telemetry logging. |
