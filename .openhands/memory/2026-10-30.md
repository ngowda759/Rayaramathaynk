## PR #366 follow-up — quote write-on-read + unauthenticated admin routes (rev 2)

Branch `audit/production-supabase-readiness`, commit `bf2dd75` on top of `fb21696`.
Two real defects found while correcting the settings inventory:

- **`QuoteService.getTodaysQuote` wrote to the DB.** Reached from the public homepage render
  (`app/(public)/page.tsx` → `services/daily-spiritual.server.ts:196` → `getTodaysQuote`) and
  from `GET /api/quotes/today`. It called `seedDefaultQuotes()` when no active quote existed
  (33 inserts) and fired `incrementViewCount` (a `quotes` UPDATE) on every non-cached call.
  So a page view or a **build-time prerender** could mutate `quotes`. Removed both writes from
  the read path in `services/quote.server.ts` *and* the near-duplicate `services/quote.service.ts`
  (they are byte-similar copies — always edit both). `seedDefaultQuotes`/`incrementViewCount`
  remain as explicit operations.
- **Four admin quote endpoints had no auth.** `proxy.ts` does NOT gate `/api/admin/*` (it only
  sets security headers + tracks page views), so each handler self-authenticates. Only
  `app/api/admin/quotes/route.ts` did. Unguarded: `seed` POST, `bulk` GET+POST, `cache` POST,
  `[id]` GET+PUT+DELETE. All now call `verifyAdminUser` (`@/lib/auth/admin-auth`). The admin page
  used raw `fetch` (no token) — that is *why* they were unguarded — so it was moved to
  `apiFetch` (`lib/api/fetch.ts`), which attaches the Firebase ID token. `hooks/useAdminFetch.ts`
  is the Supabase-Auth equivalent used by Raya AI admin pages; both idioms exist.
- **Gotcha:** `app/admin/quotes/page.tsx` and several other files have **trailing spaces on blank
  lines**, so `file_editor`/exact-match edits on multi-line blocks fail. Use a regex with
  `[ \t]*` for blank lines (see the throwaway scripts pattern) or match single lines.

## Process lesson (user feedback)

- **Batch pushes on a PR branch.** Each `git push` to a Vercel-connected branch starts a *new*
  preview build, and Vercel cancels the previous one — which shows up as a `Vercel: failure`
  ("Canceled from the Vercel Dashboard") on the superseded SHA. The user saw "lots of review
  builds". Commit locally as many times as needed, then push **once** when the work is complete;
  only the final SHA's status matters.
- Reading `commits/{sha}/status` for the *latest* SHA is the right check; a `failure` on an
  older SHA is usually just supersession, not a real break.
