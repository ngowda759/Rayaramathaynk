# 2026-11-04 — F-A16 isolated integration verification (PR #382)

## Goal
High-fidelity verification of the two PROPOSED F-A16 migrations against a real Supabase
role model (not PGlite): F-A16-02 (`20261115000000_f_a16_least_privilege_defaults.sql`) and
F-A16-02b guard (`20261114990000_f_a16_public_function_execute_guard.sql`). No production
access.

## Environment
`supabase/postgres:15.19.0.018` (official Supabase image, PostgreSQL 15.19) in a disposable
Docker container; `pg` over TCP. This image **ships `supautils`** — that is the crux.
Role model: `postgres` (non-superuser, rolbypassrls), `supabase_admin` (superuser),
`anon`/`authenticated`/`service_role`. `postgres` is **not** a member of `supabase_admin`.

## Key learnings (expensive to rediscover)
- **The official Supabase image loads `supautils`.** A non-superuser `postgres` CAN
  `CREATE EVENT TRIGGER` on it (owned by `postgres`), whereas stock PostgreSQL returns
  `permission denied to create event trigger` / `Must be superuser`. So the F-A16-02b
  guard IS installable on Supabase. `supautils` is a shared library, not a `pg_extension`
  row; config at `/etc/postgresql-custom/supautils.conf`; `supautils.privileged_role =
  supabase_privileged_role` (postgres is a member of it).
- **RESIDUAL (measured): a `supabase_admin`-created function in `public` keeps the
  implicit PUBLIC EXECUTE — the guard event trigger does NOT fire for it.** Isolated by
  contrast: the trigger DOES fire for a superuser on stock PG 17.11, and on a Supabase
  image with `supautils` removed. Mechanism: `supautils` runs privileged DDL in a
  non-`origin` replication role, and a default `ENABLE ORIGIN` event trigger does not fire
  then. `ENABLE ALWAYS` does not help. This is why PGlite (superuser) can't see it and why
  the guard "works" in PGlite. Documented in the guard header + verification doc; low
  severity (anon/auth can't reach without explicit grant; residual is service_role).
- **A fresh Supabase-image DB is owned by `supabase_admin`**, so `postgres` lacks CREATE
  on `public`. Fix: connect as the superuser and
  `ALTER DATABASE <db> OWNER TO postgres; ALTER SCHEMA public OWNER TO pg_database_owner;`
  (real Supabase projects own the DB as `postgres`). `ALTER DATABASE … OWNER` fails unless
  run as a superuser.
- **The `public`-scoped `pg_default_acl` query returns 6 rows** (postgres + supabase_admin
  × r/S/f), not 24. 24 is across all schemas (public, storage, extensions, graphql,
  graphql_public, realtime, auth). `F-A16_EXECUTION_CHECKLISTS.md` wrongly said 24 for the
  public-scoped query — corrected.
- **A `REVOKE` a role may not perform only WARNS** (`no privileges could be revoked`) and
  leaves the routine world-executable; it does not raise. Hence the guard's fail-closed
  `has_function_privilege` re-check. `has_function_privilege('anon', oid, 'EXECUTE')`
  returns true for a PUBLIC-granted function even though anon has no direct grant.
- **Docker Desktop NAT means `host` lines use `scram-sha-256`**, so test login roles need
  a password (`trust` only applies on the container's own `127.0.0.1`). Local socket is
  `trust` for `supabase_admin`, `peer` for others.
- **Role drop after use**: `DROP ROLE` fails if the role still has privileges on a schema.
  Use `REVOKE ALL ON SCHEMA public FROM r; DROP OWNED BY r; DROP ROLE r;`.
- **`create` file tool refuses to overwrite** — `rm` first.
- **Don't create a `/tmp/.../x.sh` heredoc with a top-level `echo`/multiple statements and
  then `bash` it in the same command** — the terminal tool rejects "multiple commands" if
  the text contains blank-line-separated blocks. Put it in a file then run it.

## Follow-up pass (commit 5d886452) — the residual is REACHABLE and now CLOSED

### Corrected the mechanism (the earlier note was WRONG)
The residual is **NOT** the replication role. Measured directly inside the trigger: the
session replication role is `origin` at fire time for every creator. The real cause is
`supautils`'s own **`fmgr` hook** (supabase/supautils `src/supautils.c`):
`supautils_fmgr_hook` attaches to functions `RETURN event_trigger`; `skip_event_trigger()`
skips when the executing role is a **superuser** and the trigger function is **not
superuser-owned**. (Also skips for a reserved role.) So a `postgres`-owned guard is a
no-op for a `supabase_admin` creator. `ENABLE ALWAYS` is irrelevant — the hook is not the
`ENABLE ORIGIN` filter. Firing matrix (measured): `postgres`-owned trigger fires for
`postgres`+members, NOT `supabase_admin`; `supabase_admin`-owned trigger fires for all.

### The residual is REACHABLE, not `service_role`-only
On a fresh Supabase DB, `anon` and `authenticated` hold `USAGE` on `public`. A SECURITY
DEFINER function created by `supabase_admin` in `public` (no explicit grant) was invoked
successfully via `SET ROLE anon; SELECT public.<fn>()` — the PostgREST path. So this is a
real anon/authenticated privilege path, not a theoretical one.

### Closure (implemented, verified)
`supabase_admin`-owned guard fires for ALL creators incl. `supabase_admin`. `postgres`
cannot install one (`SET ROLE supabase_admin` denied; `ALTER EVENT TRIGGER … OWNER TO`
needs a superuser). So it is a **required owner-run step**: new file
`docs/audits/F-A16_OWNER_RUN_supabase_admin_function_guard.sql` (separate from the defaults
owner-run file, to keep each file's "changes only X" unit invariant checkable — the guard
file has no `ALTER DEFAULT PRIVILEGES`). Two-guard design: migration's `postgres`-owned
guard (backstop, ordinary creators) + owner-run `supabase_admin`-owned guard (superuser
creator). End-to-end: t_pg/t_su → anon=false auth=false svc=true.

### Two integration-harness defects found and fixed (would have passed vacuously)
1. `CREATE DATABASE` does **not** inherit the platform's `public` default ACLs (the image
   applies them at cluster init via `docker-entrypoint-initdb.d/init-scripts/00000000000000-initial-schema.sql`).
   Without them a new function has no explicit anon/auth EXECUTE, the guard removes
   nothing, and A.1 passes for the wrong reason. Fix: `beforeAll` reproduces the image's
   `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES/FUNCTIONS/SEQUENCES TO
   postgres, anon, authenticated, service_role` for both `postgres` and `supabase_admin`.
2. B.4/B.7 assert the *pre-closure* state, which B.7 installs → 2nd run on the same DB
   failed. Fix: both `DROP EVENT TRIGGER IF EXISTS f_a16_public_fn_guard_su` first.
   Suite now deterministic fresh + re-run (verified 3x + fresh).
