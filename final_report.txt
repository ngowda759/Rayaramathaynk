AFFECTED DATA FLOW
Data exists in Firestore but is not loading correctly in the UI primarily due to disjointed collections for the "Sevas" feature and missing security rules.
1. The public dropdown in `components/home/SevaBooking.tsx` loads data via `poojaService.getPoojas()`, which queries the `dailyPoojas` collection.
2. The Admin Receipt module manages Sevas through `/api/admin/receipt-sevas/route.ts` and `services/seva.service.ts`, which write to and read from the `sevas` collection.
Because admin-configured sevas go into `sevas`, but public booking queries `dailyPoojas`, the public UI sees an empty state. Furthermore, `dailyPoojas` is completely missing from `firestore.rules`, causing public reads to fail with "Permission Denied". Errors caught in `poojaService.getPoojas()` could be swallowed or logged, resulting in an empty array `[]` being returned.

HIGHEST READ-COST OPERATIONS

| File | Function | Collection | Read pattern | Risk |
|------|----------|------------|--------------|------|
| `app/api/public/stats/route.ts` | `GET` | `donations` | Full collection read via `getDocs(query(..., where("status", "==", "completed")))` to calculate unique donors. | HIGH |

SEVAS DROPDOWN
The complete failure path for the public Sevas dropdown:
1. User visits the Sevas page.
2. `SevaBooking.tsx` mounts and calls `poojaService.getPoojas()`.
3. `poojaService.getPoojas()` executes `getDocs(query(collection(db, "dailyPoojas"), orderBy("displayOrder", "asc")))`.
4. This query checks the `dailyPoojas` collection, which fails because `dailyPoojas` is not defined in `firestore.rules`, resulting in a Permission Denied error.
5. Even if the rule existed, if the admin manages sevas in the `sevas` collection, the `dailyPoojas` collection is empty.
6. The `poojaService` mapping or calling component receives an empty array (or fails).
7. `SevaBooking.tsx` filters `data.filter((item) => item.isActive && item.sevaAmount > 0)`.
8. The state `poojas` is set to `[]`.
9. The dropdown (`<select>`) in the UI receives an empty array and only shows the default "Select a seva" option.

QUOTA RISK
Firestore quota exhaustion cannot be confirmed from repository evidence alone. However, the current architecture has highly inefficient read patterns that could easily consume the free-tier quota.
- **Polling Risk:** `useDonationNotifications.ts` polls every 60 seconds (1,440 reads per user per day for just 1 document, up to 28,800 reads per user per day for 20 documents).
- **Full Collection Reads:** `app/api/public/stats/route.ts` does a full collection read on `donations` to count unique emails/phones. If a temple has 10,000 donations, a single request to the public stats API consumes 10,000 reads.

EVIDENCE
- **Collection Mismatch:** `services/pooja.service.ts` uses `const COLLECTION_NAME = "dailyPoojas";`, whereas `app/api/admin/receipt-sevas/route.ts` uses `const RECEIPT_SEVAS_COLLECTION = "sevas";`.
- **Missing Rules:** `firestore.rules` has no match for `dailyPoojas`.
- **Polling:** `hooks/useDonationNotifications.ts` line 64: `const interval = setInterval(fetchDonations, 60000);`
- **Full Collection Reads:** `app/api/public/stats/route.ts` line 54: `const donorsSnapshot = await getDocs(donorsQuery);` followed by iterating over all docs to populate a `Set`.
- **Error Swallowing:** (General observation in services like `services/seva.service.ts` line 14: `catch (error) { ... return []; }`)

RECOMMENDED FIXES
1. **Fix Sevas Data Flow:** Standardize on either `sevas` or `dailyPoojas` for the SevaBooking public component, ensuring it reads from the same collection that administrators use to add/update Sevas.
2. **Fix Security Rules:** Add explicit read rules for whichever collection is chosen for public sevas/poojas.
3. **Optimize Unique Donors Query:** Refactor the public stats API to avoid full collection reads on `donations`. Use an aggregated counter document or a separate scalable tracking mechanism for unique donors.
4. **Refactor Notification Polling:** Change `useDonationNotifications` to use `onSnapshot` (with appropriate limits/filters) or increase the polling interval significantly to avoid unnecessary reads.
