AFFECTED DATA FLOW
Data exists in Firestore but is not loading correctly in the UI primarily due to disjointed collections for the "Sevas" feature.
1. The public dropdown in `components/home/SevaBooking.tsx` loads data via `poojaService.getPoojas()`, which reads from the `dailyPoojas` collection.
2. However, the Admin Receipt module manages Sevas through `/api/admin/receipt-sevas/route.ts` and `services/seva.service.ts`, which write to and read from the `sevas` collection.
Because admin-configured sevas go into `sevas`, but public booking queries `dailyPoojas`, the public UI sees an empty state or only fallback data. Furthermore, any error caught in `poojaService.getPoojas()` is swallowed or logged and an empty array is returned, making it look like "no data exists".
The `app/admin/sevas/page.tsx` was also oddly found querying `volunteer.service.ts` (Members/Volunteers collections).

SEVAS DROPDOWN
The complete failure path for the public Sevas dropdown:
1. User visits the Sevas page.
2. `SevaBooking.tsx` mounts and calls `poojaService.getPoojas()`.
3. `poojaService.getPoojas()` executes `getDocs(query(collection(db, "dailyPoojas"), orderBy("displayOrder", "asc")))`.
4. This query checks the `dailyPoojas` collection. If the admin manages sevas in the `sevas` collection instead, the `dailyPoojas` collection is empty.
5. The `poojaService` maps the empty snapshot to an empty array.
6. `SevaBooking.tsx` filters `data.filter((item) => item.isActive && item.sevaAmount > 0)`.
7. The state `poojas` is set to `[]`.
8. The dropdown (`<select>`) in the UI receives an empty array and only shows the default "Select a seva" option.

QUOTA RISK
The current architecture can realistically consume the free-tier Firestore quota (50,000 reads/day) under moderate traffic.
- **Polling Risk:** `useDonationNotifications.ts` polls every 60 seconds (1,440 reads per user per day for just 1 document, up to 28,800 reads per user per day for 20 documents). Just 2-3 users leaving the app open in a tab for a day could exhaust the quota.
- **Full Collection Reads:** `app/api/public/stats/route.ts` does a full collection read on `donations` to count unique emails/phones. If a temple has 10,000 donations, a single request to the public stats API consumes 10,000 reads. 5 page loads = quota exhausted.

EVIDENCE
- **Collection Mismatch:** `services/pooja.service.ts` uses `const COLLECTION_NAME = "dailyPoojas";`, whereas `app/api/admin/receipt-sevas/route.ts` uses `const RECEIPT_SEVAS_COLLECTION = "sevas";`.
- **Polling:** `hooks/useDonationNotifications.ts` line 64: `const interval = setInterval(fetchDonations, 60000);`
- **Full Collection Reads:** `app/api/public/stats/route.ts` line 54: `const donorsSnapshot = await getDocs(donorsQuery);` followed by iterating over all docs to populate a `Set`.
- **Error Swallowing:** (General observation in services like `services/seva.service.ts` line 14: `catch (error) { ... return []; }`)

RECOMMENDED FIXES
1. **Fix Sevas Data Flow:** Standardize on either `sevas` or `dailyPoojas` for the SevaBooking public component, ensuring it reads from the same collection that administrators use to add/update Sevas.
2. **Optimize Unique Donors Query:** Refactor the public stats API to avoid full collection reads on `donations`. Use an aggregated counter document or a separate scalable tracking mechanism for unique donors.
3. **Refactor Notification Polling:** Change `useDonationNotifications` to use `onSnapshot` (with appropriate limits/filters) or increase the polling interval significantly to avoid unnecessary reads.
